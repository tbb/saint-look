# Подготовка пробы стилизованной примерочной (#44)

Этот инструмент проверяет путь **локальные фотографии → локальные ответы признаков/генерации/сегментации → журнал → отчёт отдельных вещей и сочетаний**. Он не умеет обращаться к JEV, fal или Photoroom. Никаких ключей ему не нужно; даже наличие ключей в окружении не включает live-режим. Красный тестовый квадрат в результате — ожидаемая транспортная заглушка, а не иллюстрация вещи и не доказательство качества.

Реальная проба — отдельная задача #45 после согласования бюджета и источников. Положительный go/no-go, а не просто закрытая исследовательская задача, открывает реализацию продукта. При no-go зависимые задачи нельзя считать готовыми.

## Воспроизведение без расходов

Нужен Node 24; установка npm-пакетов не требуется. Команды выполняются из корня репозитория.

В первом терминале:

```bash
node scripts/fitting/fixture-server.mjs
```

Сервер слушает только 127.0.0.1 и печатает адрес со свободным портом. Во втором терминале подставить этот адрес; каталог результата должен быть новым:

```bash
node scripts/fitting/experiment.mjs \
  --plan scripts/fitting/plan.json \
  --out /tmp/saint-look-fitting-local-result \
  --fixture-url http://127.0.0.1:PORT \
  --max-requests 60 \
  --max-cost-microusd 4065036
```

Открыть `review.html` в каталоге результата. `answer-key.json` раскрывает вариант; оценщику передавать только HTML до заполнения оценки. `report.json` содержит план, SHA исходников и шаблона, прогноз, фактически зарезервированную оценку и количество завершённых/неизвестных этапов. `plan.json` в каталоге результата фиксируется до первого запроса. `journal.jsonl` записывает начатые и терминальные состояния операций с fsync; начатый запрос без терминального события после crash считается неизвестным и не повторяется автоматически. Существующий каталог нельзя перезаписать или незаметно возобновить.

Тесты:

```bash
node --test scripts/fitting/*.test.mjs
```

Они поднимают собственные loopback HTTP-серверы и не скачивают изображения. Workflow `Fitting experiment local checks` запускает только эти тесты, без AI-секретов и iOS Simulator. Изменение самого общего CI-workflow по-прежнему требует общих проверок.

## Что есть в наборе

`plan.json` фиксирует **10 вещей / 12 фото** и 5 комбинаций. Реальные перед/спинка одной вещи есть у butterfly hoodie и музейной футболки; это 2 дополнительных input-set, а не 4. Все фото лежат в `fixtures`, имеют SHA, источник, автора, лицензию и описание преобразований. Перепроверка SHA происходит до отправки первого запроса. Подробности, условия атрибуции и ограничения: [исходники и рубрика](../../docs/research/fitting-fixtures.md).

Открытые лицензии разрешают использование с указанными условиями; они не заменяют проверку условий конкретного API. Публичный отчёт с изменёнными изображениями должен сохранять атрибуцию и требуемую лицензию производной (в частности ShareAlike), отдельно от лицензии программного кода. Манифест не даёт blanket-разрешения отправлять фото любому поставщику. Личные фотографии пользователя в набор не включены.

Внутри протокола fixtures:

- `POST /attributes` принимает itemId, single/multi input, data URI фотографий и photoRoles; возвращает плоский объект `features` с тестовыми нормализованными значениями.
- `POST /generate` принимает те же фото/роли, общий SVG-template, версию шаблона, параметры и, только в B, признаки. Возвращает `pngBase64`.
- `POST /segment` принимает предыдущую PNG и возвращает `pngBase64`. Этап необязательный по плану, но в основной оценке расходов предусмотрен для каждого результата.

Это **наш локальный протокол, не payload JEV или fal**. JEV возвращает Choice/Noul/Score, а fal использует отдельный queue-контракт. Преобразование и реальный адаптер принадлежат #45. Проверка PNG в harness проверяет конверт/габариты; полное декодирование, alpha и визуальное качество здесь не подтверждаются и обязательны для реального адаптера.

## Сравнение и визуальный шаблон

Для каждой вещи создаём single-A и single-B. Для вещей с дополнительными фото также multi-A и multi-B. Один ответ признаков используется для пары; в A признаки вообще не передаются. Ракурс/стиль/настройки остальных входов одинаковы. PhotoRoles различают перед и спинку, чтобы не переносить задний принт вперёд.

В отчёте варианты получают устойчивые псевдослучайные коды из seed и сортируются по ним. Результаты разных веток не подписаны «лучше/хуже»; расшифровка отдельная. Это слепая разметка для человека, а не криптографическое скрытие алгоритма. Сравнение multi-композиций использует single у вещей без дополнительных фото и явно записывает разрешённые input-set в answer-key.

`mannequin.svg` — перенос геометрии предоставленного HTML-референса в самостоятельный векторный шаблон360×560, без одежды и без обещания физической посадки. Рисунок фронтальный, руки немного разведены. Предлагаемая цель для иллюстраций — **полный прозрачный canvas360×560** или эквивалентный масштаб с сохранением aspect ratio. Renderer накладывает весь canvas каждого слоя на весь canvas манекена, не сжимает его второй раз в категорийный прямоугольник. Порядок: низ, обувь, слои тела в порядке выбора, голова. Необычные перекрытия остаются предметом реальной пробы.

Документированный candidate endpoint может возвращать квадратный PNG. В #45 нужно проверить поддерживаемый aspect ratio или зафиксировать единое размещение canvas360×560 внутри квадратного1024×1024 с обратимым преобразованием для всех результатов. Нельзя принять растяжение или индивидуальный случайный crop за нормализацию. Текущий локальный тестовый квадрат демонстрирует транспорт и **не является** геометрически пригодным слоем.

Начальные опоры: плечи(133,151)/(227,151), центр пояса(180,265), щиколотки(154,490)/(206,490), подошвы y520. Они задают позу, но не заставляют каждый силуэт иметь одинаковую ширину. Стиль: мягкая сдержанная иллюстрация, ограниченный объём, без карикатурной обводки; цвета вещи не перекрашиваются под палитру приложения.

## Предварительно фиксируемая рубрика

Версия рубрики `fitting-feasibility-v1` включена в plan. До настоящей генерации заморозить её вместе с SHA плана/шаблона. Оценивать 0–2: узнаваемость/тип, цвета, пропорции, конструкция/фактура, отличительные детали/принт, совместимость с позой. Только невидимые отличительные детали могут быть N/A и исключаться из знаменателя.0 — непригодно;1 — узнаваемо с отклонением;2 — соответствует в масштабе использования.

У выбранной ветки должны пройти минимум 8 из 10 вещей; проход каждой требует >=80% возможного балла, ни одного 0 и отсутствия hard fail. Hard fail: другая вещь, чужая одежда/тело, потерянный характерный принт, выдуманная читаемая надпись или неверная сторона. Обязательны открытая куртка, длинный верх, хотя бы один принт, низ и обувь. Все 5 обязательных сочетаний должны работать без ретуши каждого нового сочетания; однократная калибровка отдельной вещи допустима, если заранее включена в процесс и стоимость.

Это инженерная рубрика для проверки гипотезы, **не согласованная оценка качества готового продукта**. Успех узкой выборки не доказывает головные уборы, высокие сапоги, юбки или все типы одежды. Дополнительные фото в 2 случаях дают разведочный результат. Если вариант с JEV не улучшает качество, не объявлять его обязательным из-за исходной идеи. Локальные fixtures всегда имеют `qualityEvidence:false` и не могут дать go.

## Предлагаемый бюджет #45

Первичный обзор: [поставщики и ограничения](../../docs/research/fitting-providers.md). Для текущих N=10/M=2:

| Этап | Базовых вызовов | С разрешаемыми повторными слотами | Резерв на вызов |
| --- | ---: | ---: | ---: |
| JEV normal context |12|14|2753microUSD — консервативная оценка, не flat price |
| Nano Banana Pro1K |24|28|150000microUSD |
| Сегментация BRIA без prompt |24|28|18000microUSD |
| Итого |60|70|$4.065036 базово; $4.742542 с резервом повторов |

Предложенный общий cap потребления — $10, **пока не разрешение расходовать деньги**. Число вызовов не увеличивается до исчерпания всех $10. В research приведён потолок N=12/M=4 ($6.097554,90 слотов) на случай отдельно согласованного расширения; он не меняет текущий набор автоматически. Пополнение аккаунта и налоги не равны потреблению API и не согласованы этой таблицей.

`ratesMicrousd` — зарезервированная верхняя оценка по зафиксированным опубликованным ставкам. Для JEV фактическая цена определяется input_tokens; отсутствие usage/неизвестный исход не освобождает резерв. В локальном harness actualCost всегда 0 и отдельно от резерва. Перед real-dispatch ставки перепроверяются. Ограничитель нашего клиента ограничивает dispatch по фиксированным ставкам, но не является гарантией абсолютного hard cap биллинга поставщика.

Harness не делает автоматических повторов даже на локальном сервере. Повторные слоты в таблице нужны только для будущих явно разрешённых попыток #45. Там должен быть общий долговечный ledger всего эксперимента, который нельзя сбросить новым каталогом результата. Для fal нужно отключить SDK retries и внутренние retries/requeue (`X-Fal-No-Retry:1` и `x-app-fal-disable-fallback:true`; [официальные параметры fal](https://fal.ai/docs/documentation/model-apis/common-parameters), перепроверить перед запуском). Receipt сохраняется до polling; потерянный receipt означает unknown, не новую оплачиваемую отправку. Segmentation и другие вспомогательные запросы также резервируются.

Длительность генерации пока **не измерена**. До #45 нельзя обещать секунды на вещь; в пробе записать отдельно время ожидания очереди и обработки и остановку по лимиту ожидания. Текущий CLI имеет ограниченное абсолютное время каждого локального HTTP-запроса (по умолчанию 10 секунд, максимум 60 секунд); timeout не разрешает повтор.

## Что #44 не делает

Не выбирает поставщика по несуществующему результату, не запускает реальные API, не регистрирует аккаунты, не читает креденшелы, не меняет backend/app, не запускает перегенерацию гардероба. Показ успешного transport-check не закрывает вопросы качества, прозрачности, сложного наложения или доступа к API. Это явно измеряемая работа #45.
