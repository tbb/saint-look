# Ручной адаптер пробы #45

`trial.mjs` — подготовка реальной пробы. Его тесты работают только с localhost: они не измеряют качество иллюстраций, доступность аккаунта или реальный биллинг. #45 остаётся открытой до разрешённого запуска, визуальной оценки и решения go/no-go. Production backend/iOS этим кодом не меняются. Выбранная цепочка: Photoroom sandbox → JEV → Nano Banana → при непрозрачном результате — Photoroom sandbox для финального прозрачного слоя. Реальных вызовов при подготовке не было; BRIA не используется.

## Локальная проверка

Из корня репозитория, Node 24:

```bash
npm --prefix backend ci --ignore-scripts
node --test scripts/fitting/*.test.mjs
node scripts/fitting/trial.mjs --describe --plan scripts/fitting/plan.json
```

Последняя команда только декодирует локальные источники и печатает fingerprint, закреплённые модели и верхний резерв. Тесты поднимают собственный сервер с контрактами JEV/fal; старый `fixture-server.mjs` реализует другой, упрощённый протокол #44. Наличие реальных ключей в окружении не переключает тесты на внешний API. Автоматический PR/push CI и произвольный workflow блокируют `--live` до чтения допуска и ключей. Отдельный вручную разрешённый эксперимент описан ниже.

Набор ограничен 10 вещами / 12 фото; первый ракурс определяет single, полный список — multi. Финитные признаки JEV (`fitting-observable-v2-photoroom-sandbox`) описывают видимую форму, длину, рукава, рисунок/расположение/размер, горловину, застёжку, поверхность, капюшон/карманы/манжеты/надписи, тип и цвета. Неуверенный Choice становится `unknown`. Нет свободного угадывания бренда, состава ткани, текста или посадки на человеке. JEV получает prepared/original пары с ролями; оригинал помогает не принять sandbox-watermark за принт. JEV не получает изображение манекена.

Все 12 исходных фото предварительно обрабатываются Photoroom sandbox ровно по одному разу; подготовленные артефакты кешируются для single/multi. Nano получает original/prepared пары с явно подписанными ролями, общий template последним и указание игнорировать watermark. A/B используют одинаковые изображения, seed, позу, формат и настройки; только B получает признаки. Общий SVG360×560 вписан с сохранением пропорций в белый square1024×1024 (`square-letterbox-1024-v1`). Именно этот PNG передаётся модели и служит основой отчёта. Генерация обязана быть квадратной; готовый непустой выход с usable alpha используется сразу, финальный Photoroom помечается skipped без расхода quota slot. Полностью прозрачный выход отвергается. Финальный Photoroom должен сохранить её полные размеры и иметь ненулевой непостоянный alpha. Это проверяет контракт холста, но не доказывает правильность расположения одежды внутри него. В композициях сначала низ/обувь, затем выбранные слои тела, затем голова.

## Допуск перед реальным запуском

Не создавать допуск от имени пользователя и не считать согласование общей спецификации разрешением расходовать бюджет. Сначала подтвердить аккаунт fal, бюджет, условия поставщиков/исходников и ставки; затем отдельный закрытый JSON вне git. Схема полей (это описание, **не готовое разрешение**):

| Поле | Требование |
| --- | --- |
| `mode` | `live` |
| `planSha256` | Точное значение `--describe` после окончательного выбора плана |
| `outputDirectory` | Один согласованный абсолютный путь к закрытому каталогу всей пробы |
| `budgetMicrousd` | Явно разрешённый целый бюджет, не более 5000000 |
| `maxCalls` | Объект с потолками `preparation`, `attributes`, `generation`, `segmentation`; максимум `12/14/28/28` соответственно (до82 вызовов, включая до40 Photoroom sandbox). Базово `preparation:12, attributes:12, generation:24, segmentation:24` (до72 вызовов, включая бесплатные sandbox-слоты) |
| `sourceTermsReviewed`, `providerTermsReviewed`, `paidCallsAllowed` | Все строго boolean `true`, только после фактического согласования |
| `approvedBy` | Кто разрешил пробу |
| `priceCheckedAt` | ISO timestamp фактической перепроверки цен, не старше 24 часов |

Fingerprint включает SHA файлов runner (включая `manual-trial.mjs` и `trial-admission.mjs`), переиспользуемого JEV/taxonomy и dependency lockfile, байты плана, SHA фото и SVG, версию runner/frame и SHA растеризованного шаблона. Допуск дополнительно привязывает выходной каталог; ledger привязан к SHA самого допуска. Изменение плана, источников, допуска или каталога не является способом начать бюджет заново. Не удалять/переписывать ledger и не выдавать новый допуск на повтор неизвестного запроса.

## Ручной запуск с GitHub Secrets

Ключи хранятся в repository Actions secrets: `FAL_KEY`, `TYPESAFE_API_KEY`, `PHOTOROOM_SANDBOX_API_KEY`. Само добавление ключей или пополнение аккаунта не означает согласование бюджета. Первая партия ограничена предложенным cap $5 и максимумом 82 операций; этот cap не описывает баланс аккаунта. Пользователь выбрал GitHub для хранения ключей; отдельный workflow `Manually approved fitting trial` (`fitting-live-trial.yml`) получает их только в шаге запуска пробы. Обычный `Fitting experiment local checks` остаётся на локальных ответах без секретов.

Порядок для оператора после согласования расходов:

1. Взять точный текущий SHA `main` и дождаться успешного `fitting-local` в `Fitting experiment local checks` именно для этого SHA: push или ручной `workflow_dispatch` на main. PR-проверки не принимаются. Эта проверка относится к инструменту пробы; отдельная iOS-приёмка не заменяется ею.
2. На этом SHA выполнить `--describe` из примера выше и записать `planSha256`. Перепроверить цены, лицензии публичных фото и условия обработки/хранения изображений; записать время реальной проверки цен в UTC. Для `approval_reference` использовать ссылку на публичное описание плана в #45, например [предложение ограниченной пробы](https://github.com/tbb/saint-look/issues/45#issuecomment-6455068166). Этот комментарий описывает план и сам по себе не является разрешением расходов. Публиковать сведения о ключах или балансе аккаунтов не требуется.
3. После согласования расходов один раз вызвать `fitting-live-trial.yml` через `workflow_dispatch` на `main`: `revision`, `plan_sha256`, `budget_usd=5`, `price_checked_at` (ISO UTC, не старше 24 часов), `approval_reference` (ссылка на описание плана), `reviewed_terms=true`, `approve_paid_calls=true`. Явные подтверждения ручного запуска оформляют допуск; не ставить их автоматически на основании наличия кредита. В JSON допуска ссылка сохраняется как `planReference`.
4. Сохранить артефакты `fitting-45-admission` и `fitting-45-evidence` до истечения семи дней. Второй содержит только допуск, ledger, JSON/HTML-отчёты и изображения публичной выборки. Ключи, окружение runner и его временные файлы туда не входят. Личные фотографии через этот workflow не разрешены.

`reserve` не получает ключи провайдеров. Он проверяет событие, repository, workflow/ref, attempt=1, совпадение SHA workflow/checkout/текущего main, fingerprint, допуск и успешную профильную проверку. Права `contents:write` нужны ему только для атомарного создания **одного фиксированного** Git ref `refs/tags/fitting-trial-45-reserved`; исходный код/ветка main не меняются. Ref указывает на проверенный SHA и не удаляется/не заменяется кодом.

Этот ref — постоянная резервация допуска #45, не журнал фактического списания денег. Он переживает потерю runner, лога и артефактов. Новый dispatch, другое имя выходного каталога, изменение плана или кнопка Re-run не дают новый бюджет: повторное создание ref отклоняется, а `run_attempt != 1` запрещён. Даже если создание ref завершилось неопределённым ответом или выполнение упало до первого платного запроса, автоматический повтор недопустим. Нужна ручная сверка состояния ref, receipt/ledger и биллинга; удалять ref ради нового запуска нельзя. Продолжение или новая проба требуют отдельного решения с учётом уже сделанных и неизвестных операций.

После резервации admission связывает run id/attempt, actor, repository, SHA, workflow, fingerprint, SHA допуска и абсолютный выходной каталог. Job `experiment` имеет только read-права, забирает admission из того же run и передаёт его в `trial.mjs --manual-admission`. CLI повторно проверяет контекст до чтения ключей. Снятие `CI`/`GITHUB_ACTIONS`, общий флаг разрешения и paid fallback не используются.

`concurrency` сериализует запуск без отмены текущего. Ledger по-прежнему сохраняет резерв на диск до каждого POST. Загрузка evidence выполняется с `always()`, включая обычную ошибку пробы; жёсткая потеря runner или сбой upload могут оставить неполные/отсутствующие артефакты. В этом случае постоянный ref всё равно запрещает новую попытку. Workflow не возобновляет платный этап автоматически на новой машине.

## Существующий запуск вне GitHub Actions

CLI также сохраняет прежний режим для уже согласованного запуска вне CI с постоянным локальным ledger. После получения допуска оператор задаёт `FAL_KEY`, `TYPESAFE_API_KEY` и отдельный `PHOTOROOM_SANDBOX_API_KEY` безопасным способом вне истории shell/чата и вручную запускает:

```bash
node scripts/fitting/trial.mjs --live \
  --plan scripts/fitting/plan.json \
  --approval /PRIVATE/approved-trial.json \
  --out /PRIVATE/approved-trial-output
```

Эта команда не является способом обойти уже зарезервированную GitHub-пробу: нельзя скачивать неполные результаты и выдавать новый локальный допуск/каталог вместо сверки прежних операций. Photoroom-ключ обязан начинаться с `sandbox_`; live-ключ и production fallback не принимаются. Ключи не записываются в артефакты; закрытые исходники, отчёты и ledger не коммитить. Базовый резерв текущего набора — 3633036 microUSD; proposed дополнительные слоты и $5 в `plan.json` не являются разрешением. Клиентский cap ограничивает dispatch по фиксированным ставкам, не гарантирует банковский hard cap поставщика. Для JEV сохраняются `input_tokens` и рассчитанная по ним оценка; фиксированный резерв 2753 microUSD не выдаётся за фактическую цену. Live `actualCostMicrousd` остаётся null до сверки биллинга.

## Запросы, восстановление и остановка

Для единственного измерительного JEV-запроса после остановки первой реальной пробы есть отдельный [диагностический допуск](JEV-DIAGNOSTIC.md). Он сохраняет прежний unknown/ledger, не продолжает этот runner и не снимает его reservation.

Закреплены JEV1.14.0, Nano Banana Pro edit1K/1image и Photoroom sandbox без prompt. На каждом fal submit выставляются `X-Fal-No-Retry:1`, `x-app-fal-disable-fallback:true`, Store-IO0, expiry3600, start-timeout120. SDK, retries submit и fallback отсутствуют. Store-IO0 не означает отсутствие CDN или всех логов поставщика. Результаты скачиваются немедленно: queue/CDN retention ограничен.

Для Photoroom используется закреплённый `https://sdk.photoroom.com/v1/segment`, multipart `image_file`, `format=png`, `despill=false`, `channels=rgba`, `size=full`, `crop=false`, без `bg_color`, и `x-api-key` только с sandbox-ключом. Preparation и финальная сегментация — отдельные учитываемые слоты по $0. Лимиты аккаунта (включая sandbox100/day и60/min) остаются внешними; quota/429 останавливает цепочку, не переключает её на live/другого поставщика.

Перед каждым POST резерв fsync-сохраняется в ledger, после submit receipt сохраняется до polling. Полученный receipt валидируется по UUID и точному owner/app URL; CDN разрешён только на HTTPS fal.media/v3.fal.media/v3b.fal.media, без редиректов и provider Authorization. Проверяются размер ответа, MIME, полное декодирование, число страниц, пиксели и alpha. Другой CDN host требует отдельного рассмотрения, не автоматического расширения allowlist.

Повтор той же команды продолжает GET по сохранённому receipt и использует проверенные SHA локальных результатов. Успешная генерация с упавшей сегментацией остаётся учтённой. Failed/unknown попытки не освобождают резерв. Потерянный ответ синхронного Photoroom, fal submit, JEV-ошибка или crash до сохранения receipt требуют ручной сверки; новый оплачиваемый POST автоматически не выполняется. Дополнительные оплачиваемые попытки и cancel в этом CLI намеренно не реализованы: сперва сверка ledger/поставщика и отдельное решение в рамках общего бюджета.

На процесс действует exclusive lock. После kill/crash можно явно добавить `--recover-lock`: восстановление разрешено только для умершего PID на том же хосте, под отдельным exclusive recovery guard. Если остался `.recovery`, другой хост, живой/переиспользованный PID или повреждённый lock — остановиться для ручной сверки, не удалять автоматически.

Один HTTP-запрос ограничен `--timeout-ms` (по умолчанию30000, максимум60000); один цикл polling — `--max-polls` (120, максимум300), интервалы — `--poll-ms` (1000, максимум10000). Истечение лимита сохраняет receipt и резерв; оно не доказывает остановку или бесплатность работы. Отдельно сохраняются started/submitted/first-observed-in-progress/provider-completed timestamps. Интервал polling ограничивает точность измерения очереди; результат без наблюдавшегося IN_PROGRESS не даёт точного разделения queue/compute.

## Оценка результата

`review.html` показывает исходники, результаты и сочетания с обезличенными кодами. `answer-key.json` раскрывает ветки; `report.json` и `ledger.json` предназначены оператору. Рубрика остаётся в зафиксированном плане, qualityVerdict всегда null до отдельной оценки. При публикации сохранить все атрибуции и требования ShareAlike, указанные в `plan.json`/[исследовании исходников](../../docs/research/fitting-fixtures.md). При отрицательном результате не открывать продуктовую реализацию по одному лишь успеху транспорта.

Контракты и ставки сверять по первичным источникам: [fal queue](https://fal.ai/docs/documentation/model-apis/inference/queue), [fal параметры](https://fal.ai/docs/documentation/model-apis/common-parameters), [Nano schema](https://fal.ai/models/fal-ai/nano-banana-pro/edit/api), [Photoroom sandbox](https://docs.photoroom.com/remove-background-api-basic-plan/sandbox-mode), [JEV images](https://docs.typesafe.ai/images), [JEV primitives](https://docs.typesafe.ai/primitives). Дополнительные ограничения — [обзор поставщиков](../../docs/research/fitting-providers.md).
