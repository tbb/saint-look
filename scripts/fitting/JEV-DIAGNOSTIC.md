# Однократный диагностический запрос JEV для #45

Проба [40677633168](https://github.com/tbb/saint-look/actions/runs/40677633168) на `617062d` сохранила одну готовую Photoroom sandbox-вырезку, после чего `featureAnswer` отклонил JSON-ответ JEV. Конкретное нарушенное условие не установлено: исходный ответ не был сохранён. В ledger осталась одна попытка `attributes: unknown`; генераций Nano Banana не было. Значение 2753 microUSD в прежнем ledger — резерв, не подтверждённое списание.

Этот инструмент делает только один дополнительный JEV POST для измерения формы ответа. Он не исправляет контракт JEV, не продолжает полную пробу и не получает ключи Photoroom/fal. Оригинальный `trial.mjs`, его manual admission и `refs/tags/fitting-trial-45-reserved` остаются без изменений.

## Привязка к исходной попытке

`jev-diagnostic-plan.json` закрепляет исходный run/revision и SHA исходных ledger/admission/approval, публичного фото и готовой вырезки. До резервации проверяются все SHA, формат/размеры PNG и строгая форма ledger: ровно одна completed sandbox preparation и одна unknown JEV-попытка с прежней ошибкой; ноль generation/segmentation. Старый ledger копируется побайтно и никогда не переписывается. Исходное фото нормализуется локально; его SHA должен совпасть с уже выполненной preparation.

Запрос создаётся прежним `featureRequest` из cached prepared PNG и original PNG с ролями `prepared_front`, `original_front`. Байты `trial-jev.mjs`, `trial-http.mjs`, backend JEV, taxonomy и dependency lockfile сверяются с исходным `617062d`. В обоих workflow jobs используется полная git-история, чтобы проверка исторического контракта работала на новом runner.

UUID ссылок на assets меняются при каждом построении запроса. `requestSha256` описывает только новый запрос. `semanticRequestSha256` заменяет случайные ссылки содержимым изображений через подписанные роли и фиксирует model/questions. Он не выдаётся за хэш потерянного исходного запроса.

## Ручной допуск и резерв

Workflow `One admitted JEV response diagnostic` запускается только через `workflow_dispatch` на main. Оператор указывает точный текущий SHA с успешными `fitting-local` checks, SHA256 файла `jev-diagnostic-plan.json`, свежий UTC timestamp проверки цен/условий, ссылку на описание плана #45 и явные `reviewed_terms=true`, `approve_single_probe=true`.

`reserve` не получает секретов провайдеров. После проверок baseline, исходного run/ref, main и профильного CI он атомарно создаёт отдельный постоянный ref `refs/tags/fitting-trial-45-jev-diagnostic-1`. Прежний ref не удаляется и не заменяется. Новый run, новый каталог и кнопка Re-run не создают ещё одну попытку: ref постоянный, `run_attempt != 1` запрещён, admission связан с run/SHA/manifest/output.

Диагностический учёт сохраняет первую неизвестную попытку и резервирует консервативно **$0.10 для её учёта и $0.10 для единственного нового POST**, всего $0.20 внутри прежнего cap первой партии $5. Это консервативный резерв, не фактическая стоимость. Старое значение 2753 в immutable ledger не исправляется и не освобождается; в новом сводном учёте оно включено в консервативные $0.10 предыдущей попытки. Счётчики после нового резерва: preparation 1, attributes 2 из 14, generation 0, segmentation 0. Остальная партия этим допуском не запускается.

`probe` получает только `TYPESAFE_API_KEY` в шаге запроса. До POST атомарно создаётся и fsync-сохраняется `receipt.json`; существующий receipt блокирует повтор даже после восстановления файлов без скрытого состояния runner. Повторов, fallback и дополнительных provider-вызовов нет. Потеря runner/ответа/upload не разрешает новый запрос: постоянный ref остаётся, исходы сверяются вручную.

## Что сохраняется

`response.json` записывается **до** вызова неизменённого `featureAnswer`. Это whitelist не более 64 KiB: HTTP status, нормализованный вид content-type, длина/SHA тела, model, usage.input_tokens, ожидаемые ответы с числовыми/перечислимыми полями и shape metadata. Неизвестные строки заменяются фиксированными маркерами; неизвестные имена полей не копируются. Сохраняются типы, наличие полей и количества лишних/пропущенных ключей. Для больших неправильных probability objects число лишних ключей сохраняется отдельно, а число анонимных placeholders ограничено.

Headers, raw body, assets, base64 изображений, произвольные сообщения провайдера и свободный текст не сохраняются. Для model сохраняется только узкий идентификатор `jev` либо `jev-` с одной–тремя числовыми группами по 1–3 цифры (длина до 20); остальные строки редактируются. Это позволяет заметить другой model-ID без ещё одного платного измерения. Невалидный JSON даёт только транспортные метаданные без фрагмента ошибки. Числа вне диапазона, неверный model (включая разрешённый для наблюдения alias), отсутствие usage и невалидные probabilities по-прежнему отклоняются; capture не ослабляет контракт.

Если исходный ответ проходит валидатор, отдельно сохраняются `features.json` и input token count для последующего рассмотрения возможности переиспользования. Если нет — receipt остаётся failed/unknown и слот не возвращается. Расход по usage остаётся оценкой, actual cost — неизвестным до сверки.

Артефакт `fitting-45-jev-diagnostic-evidence` загружается с `always()` и содержит только admission, копии трёх прежних JSON, подготовленный PNG, receipt, whitelist response и features при наличии. Срок хранения — 7 дней. Жёсткая потеря runner/upload может оставить evidence неполным; это не отменяет reservation.

## Офлайн-воспроизведение

После скачивания evidence в каталог `/PRIVATE/jev-diagnostic`:

```bash
node scripts/fitting/jev-diagnostic.mjs replay \
  scripts/fitting/jev-diagnostic-plan.json /PRIVATE/jev-diagnostic
```

Команда не использует ключи или сеть. Она сверяет hashes baseline/snapshot, восстанавливает тот же семантический запрос и вызывает `featureAnswer` на сохранённой проекции. Candidate parser можно менять для локального red/green loop; изменение model/questions/images отклоняется сравнением semantic hash. Типы/наличие/значения в snapshot помогают назвать конкретное нарушенное условие; сам общий текст ошибки не доказывает причину.

Локальные контрактные проверки: `node --test scripts/fitting/*.test.mjs`. Они используют только loopback fixtures и никогда не подтверждают фактическую причину первой реальной ошибки без её измерения.
