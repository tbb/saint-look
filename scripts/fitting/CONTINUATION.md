# Продолжение пробы #45

Workflow `Continue the reconciled fitting trial once` продолжает оставшуюся выборку после исправления чтения округлённых вероятностей JEV. Новый запрос для белой футболки не нужен: результат восстанавливается офлайн из сохранённого ответа диагностического run `40683876977`. Это не доказывает причину первой ошибки run `40677633168`, ответ которого не сохранился.

`continuation-plan.json` закрепляет оба run/revision и SHA исходных admission/approval/ledger, диагностических admission/receipt/response, готовой вырезки и неизменённого плана. Перед резервированием проверяются исторические run/ref/actor, текущий main с успешными fitting checks, хэши файлов, размеры вырезки и семантика запроса JEV (model/questions/роли/байты изображений без случайных UUID). Исправленный parser обязан прочитать ответ офлайн. Изменение runtime создаёт новый fingerprint; старый ledger не переписывается под новый fingerprint.

В новый aggregate ledger импортируются ровно три операции:

- Готовая исходная sandbox-вырезка с тем же ключом и SHA: preparation 1, резерв $0.
- Первая JEV-попытка остаётся `unknown`. Её консервативный резерв в новом учёте — $0.10; прежний резерв 2753 microUSD сохранён отдельно, а исходные файлы копируются побайтно.
- Диагностическая JEV-попытка становится локально `completed` после повторного разбора уже полученного ответа. Её резерв — $0.10; сохраняются диагностический run, response/semantic SHA, признаки и usage. Исходный diagnostic receipt остаётся неизменным.

Первая JEV-попытка ссылается на диагностическую через `reconciledBy`; runner проверяет соответствие текущему семантическому запросу и переиспользует признаки. Это не повтор POST и не превращение неизвестной первой попытки в успешную. Обычная неизвестная попытка без такого результата по-прежнему останавливает обработку.

Начальные счётчики: preparation 1, attributes 2, generation 0, segmentation 0; общий резерв **$0.20**. На всю оставшуюся выборку нужны 11 preparation, 11 attributes, 24 generation и до 24 segmentation. Итоговые счётчики: **12/13/24/≤24**, резерв **$3.830283** внутри исходного совокупного cap **$5**, фактическое списание пока неизвестно. Ceilings **12/14/28/28** не сбрасываются. Локальные fixtures не подтверждают реальное списание или качество иллюстраций.

Для ручного dispatch указываются точный main SHA, fingerprint из `trial.mjs --describe`, SHA256 `continuation-plan.json`, свежий timestamp проверки цен/условий, ссылка на план #45 и явные `reviewed_terms=true`, `approve_paid_calls=true`, `budget_usd=5`. Это продолжение уже согласованной пробы, не дополнительный бюджет. Workflow получает предыдущий artifact через GitHub token; секреты поставщиков доступны только execution step.

Отдельный постоянный ref `refs/tags/fitting-trial-45-continuation-1` разрешает ровно один новый запуск. Прежние refs не меняются. Admission связывает новый run/revision/каталог/fingerprint и исходный SHA импортированного ledger. Проверка SHA и атомарный `continuation-started.json` выполняются перед credentials. Повторный dispatch, Re-run или изменённый seed не дают нового допуска. Потеря runner/upload требует сверки сохранённых результатов, а не удаления refs или нового POST.

Все новые ответы JEV сохраняются до валидации в ограниченной whitelist-проекции с semantic/request binding. Произвольный текст провайдера, headers, raw body и base64 не сохраняются. Ошибка следующей вещи поэтому остаётся доступной для офлайн-разбора без отдельного платного диагностического workflow. Сохранение evidence не разрешает автоматические повторы.

Новый общий helper семантического хэша повторяет алгоритм исторического `jev-diagnostic.mjs` намеренно: уже выполненный одноразовый диагностический CLI не рефакторится при продолжении. Проверка импорта настоящего ответа подтверждает совместимость хэшей.

Execution artifact сохраняет ledger, историю, ответы, PNG и review даже после ошибки. Локальная проверка: `node --test scripts/fitting/*.test.mjs` — только loopback HTTP. Качество иллюстраций оценивается отдельно по полученному review после реального запуска.
