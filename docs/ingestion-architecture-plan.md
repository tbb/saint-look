# Saint Look: ingestion-first — черновик плана нового прототипа

> Уточнение от 24 октября 2026: границы первого этапа согласованы в [документе решений](decision-ai-at-ingestion.md#первый-этап-уточнения-от-24-октября-2026) и имеют приоритет над предложениями ниже. Первый этап — карточка с вырезкой, типом и цветами, сквозная проверка на 2–3 фото, без числового SLA; векторы и подбор отложены. Временные результаты просрочены через 7 дней с загрузки; очистка после сохранения результата клиентом выполняется раньше. Для остановленного dev-backend с публичными фото согласовано исключение по физическому удалению в [ADR-0002](adr/0002-managed-dev-hosting.md). Прежние пороги A13 (18/20), требования числового SLA и иные сроки хранения ниже не являются условиями завершения или запуска первого этапа. Большой план пока не переработан под эту границу. Названия каталогов будущей реализации и организация CI определены в [ADR-0001](adr/0001-shared-repository.md); старые пути ниже не задают структуру нового кода.

Статус: предлагаемый технический план по подтверждённому [решению](decision-ai-at-ingestion.md), не реализованная функция и не разрешение на deployment/платные вызовы. Исходный handoff сохранён; архив документов прежнего прототипа удалён по решению пользователя. Совместимость с прежним API не требуется. Уточнение пользователя: пользовательских данных и production нет; новую схему и API проектируем начисто, без migration/dual-read/legacy adapters. Этот план заменяет прежнее направление «AI в момент сборки» для новой итерации; durable Ultragoal пока не переоформлен.

## 1. Результат и границы

**Фото → локальная ожидающая карточка → асинхронная обработка → готовая 2D-вырезка, автоматические признаки, представление для поиска и заранее рассчитанные рекомендации.** Никаких обязательных категории/цвета/названия. Пользовательские метки необязательны и отделены от AI-признаков.

При обычном просмотре, поиске и выборе сохранённых/готовых луков нет AI-вызова и обязательного сетевого round-trip. Оригинал сохраняется локально. 3D, виртуальная примерка, магазин, мультиустройство и публичный сервис не входят в эту итерацию. Облачный backend — обработчик и хранилище согласованных результатов, а не автоматически бессрочная копия всех оригиналов.

## 3. Минимальная архитектура

На первом этапе один backend-host, один процесс с HTTP API и фоновым worker с ограниченной конкурентностью; durable очередь и метаданные на диске, приватные файловые assets. Перезапуск процесса не теряет очередь. Не добавлять Redis, vector DB, отдельный брокер или микросервисы до доказанной потребности. Конкретный transactional storage/драйвер выбрать отдельным ADR с проверкой официальной документации, crash semantics и необходимостью новой зависимости; здесь он не выбран.

Компоненты:
- **iOS:** локальный каталог, оригиналы/превью, outbox загрузок, sync cursor, кэш рекомендаций. Приложение может быть закрыто: уже принятое сервером задание продолжается; новые локальные загрузки гарантированно возобновляются при следующем открытии, не обещаем постоянный iOS background daemon.
- **API:** авторизация, bounded upload, idempotency, статусы/дельты/результаты, удаление. Никакой синхронной AI-работы в ответе на upload.
- **Worker:** проверка → сегментация/вырезка → признаки → embedding → пары/полные луки → атомарная публикация. Промежуточные результаты приватны до валидации.
- **Storage:** записи owner/item/job/stage/result/revision/tombstone; ограниченные immutable assets, бюджетный ledger. Сам факт помещения payload в память не считается приёмом задания.

Один процесс — осознанное ограничение первой версии, не scalable production claim. Масштабирование на несколько workers требует общей транзакционной авторизации бюджета и lease, а не копий нынешнего ledger.

## 4. Данные и состояния

- `Item`: ownerID, itemID (UUID с клиента), photoRevision, userTagsRevision, tags, deletedAt/tombstone; ссылки на immutable originals/preview/cutout, состояние карточки.
- `Analysis`: analysisRevision, inputHash, pipelineVersion, model/version, category/color/pattern и confidence/unknown, embeddingVersion/dimension, конечные числовые значения; user corrections отдельно от inferred values. Embeddings не смешивать между моделями/версиями.
- `Job`: jobID, ownerID, itemID, photoRevision, pipelineVersion, стадия, попытка, lease/heartbeat, reservationID, safe errorCode; raw provider payload не писать в логи.
- `PairScore`: canonical item pair, обе analysisRevision, scoringVersion, applicability/context; отсутствие оценки не означает несовместимость.
- `OutfitSet`: anchor, supported context, wardrobeCompatibilityRevision, item analysisRevision map, scorerVersion, валидированные IDs и короткое объяснение. Пользовательские метки поиска не запускают повторный vision.

Два независимых состояния:
- Карточка: `local_pending → uploading → queued → processing → ready`; ветки `needs_attention / failed / deleted`.
- Подбор: `pending / ready / insufficient_items / failed / stale`.

Готовая вырезка доступна сразу после публикации analysis, даже если подбор ещё считается. `insufficient_items` — нормальный результат, не поломка. Ошибка не удаляет фото и не блокирует другие вещи. Неуверенность/несколько вещей → запрос выбора или пересъёмки, а не случайная категория; исправление признака опционально, не возвращает обязательную анкету.

## 5. Фото, приватность и публикация

Предлагаемый экспериментальный upload-профиль: ориентированная JPEG-копия без EXIF/GPS, до 2048px/2MiB; локальный оригинал остаётся в нынешних пределах 8MiB/40MP. Это новые **предлагаемые**, не уже утверждённые v1-лимиты: проверить качество вырезки и память до freeze API. Не отправлять оригинал с GPS для улучшения качества.

Отдельный derivative `cutout` — PNG с alpha до 2048px/4MiB; независимые проверка реального формата/пикселей/метаданных/размера и bounded decode. Для JPEG-превью сохранить строгую проверку формата: это граница безопасности, не legacy-совместимость. Предпочитать маску поверх реального изображения, не генеративную перерисовку одежды. Сегментация не должна менять цвет, форму, принт, логотип или придумывать невидимые части.

Перед первым upload объяснить серверное хранение, провайдера и удаление; очередить offline можно без отправки, отправлять только при действующем согласии. Предложение retention для отдельного утверждения: upload удалить по завершении/отказу либо максимум через 24h; результаты/embedding/cutout хранить до удаления вещи или отключения сервиса. Продуктовое согласие на async не равно согласию на конкретный retention. При истечении upload незавершённое задание возвращает явный expired, требуется разрешённая повторная загрузка.

Любой read/download/delete проверяет stable owner; неизвестный чужой ID не раскрывает существование. Никаких публичных URL, секретов/фото в Git или логах. Tombstone немедленно исключает вещь из выдачи; purge охватывает исходные upload, производные, векторы, пары, результаты и staging по задокументированной политике. Retention провайдера раскрывается отдельно, не обещать мгновенное удаление у внешнего провайдера.

## 6. Надёжность и стоимость

Внешний idempotency key = owner+operationID (стабильный UUID клиента); payload hash включает itemID/photoRevision/содержимое. Тот же ключ и hash возвращают исходное задание даже после deployment новой модели; другой payload с тем же ключом →409. При первом приёме сервер фиксирует pipelineVersion для операции. Внутренний stage key включает owner/itemID/photoRevision/зафиксированную pipelineVersion/stage; обновление pipeline само не создаёт новый платный job. Явная повторная обработка создаёт новую operationID и отдельное разрешение на расход, не переписывает исходную операцию. Полученный HTTP202 означает, что asset и job durable. Сначала bounded staging+fsync, затем транзакционный publish; orphan cleanup не трогает активные/leased assets.

Worker доставляет задания at-least-once; публикация результата idempotent. Нельзя обещать exactly-once внешний платный запрос: падение между отправкой и записью результата создаёт `usage_unknown`, сохраняет резерв, автоматический повтор этой стадии запрещён. Это относится и к lease expiry. Перед каждым новым платным stage резервировать верхнюю оценку, ограничить суммарный бюджет задачи/владельца/эксперимента. Safe pre-dispatch сбой и локальная стадия могут иметь bounded retry; неизвестный внешний результат требует reconciliation/явного решения.

При replace/delete проверять photoRevision+tombstone перед каждым внешним stage и при commit. Согласие имеет server-visible consentGeneration: приём задания и каждый новый внешний stage атомарно проверяют актуальное согласие/поколение. Серверно подтверждённый отзыв блокирует ещё не отправленные stages и их queued retries; повторное согласие само не возобновляет старые задания. Отзыв offline немедленно прекращает локальные отправки и очередится приоритетно, но не может остановить удалённый worker до доставки отзыва — это явно показывается пользователю. Уже dispatch-нутый вызов может завершиться и быть учтён; отозванные результаты не активируются. Поздний ответ не воскрешает вещь. Уже выполняющийся вызов может потребить резерв даже после отмены; результат отбрасывается. Общий budget исчерпан → blocked_budget без фонового retry storm.

Существующие семь неизвестных резервов сохраняются. План не разрешает восьмую попытку прежнего relay, ослабление protective metadata, покупку API или новую подписку. Выбор рабочего AI-пути — обязательный отдельный gate до live ingestion.

## 7. Подбор: похожесть не равно совместимость

1. Embedding — поиск похожего/кандидатов/возможных дублей. Это не достаточное доказательство сочетаемости.
2. Pair scoring оценивает кандидатов между совместимыми ролями/контекстами. Не делать по платному запросу на каждую пару: сравнение по заранее рассчитанным признакам/векторам и ограниченные batch-проверки — гипотезы для quality spike.
3. Генератор кандидатов формирует полные наборы, отдельная модель/проверка оценивает весь лук на фоне, затем сохраняет ограниченный набор. Структурные правила используются для валидности, не выдаются за AI-оценку стиля.
4. Для первой версии предложены anchor + готовые наборы, без неограниченного свободного текстового повода. Повод/новые ограничения без готового набора → честное «подбор ещё не подготовлен», не синхронный скрытый AI. Конечный список контекстов выбрать при freeze UX; старый свободный повод не переносить как будто покрытый cache.
5. При новом analysis зафиксировать wardrobeCompatibilityRevision; concurrent additions A/B должны породить и A–B после готовности обеих. Publish только при актуальных зависимостях, новые события coalesce, повторный reconciliation устраняет пропуски. Нельзя кэшировать все возможные комплекты/подмножества.
6. На телефоне готовый набор фильтруется по текущим IDs/revisions/anchor/subset. Недостаток валидных вариантов честно отображается; старые луки с неизменёнными вещами могут оставаться доступными, но удалённые IDs не возвращаются.

## 8. Предлагаемая поверхность API v2

Это эскиз, wire-schema/коды/лимиты замораживаются отдельным контрактом до реализации:
- Идемпотентная загрузка версии вещи: bounded bytes + operationID/itemID/photoRevision/hash →202 jobID/state.
- GET состояния item/job и bounded paginated delta по cursor; tombstones включены. Устаревший cursor → явный полный resync; продвижение cursor и локальная активация результатов атомарны.
- Авторизованная загрузка производных с hash/length/version; клиент проверяет bytes до активации.
- PATCH пользовательских меток с expectedRevision; конфликт не затирает локальную правку молча.
- DELETE item с tombstone и подтверждением durable приёма; удаление offline сохраняется в outbox.
- GET готовых наборов по anchor/context/revision — **нулевые provider calls**. Не запускать expensive работу из GET.

Для MVP sync при foreground/resume и bounded polling только активных заданий. Push/websocket и background upload не нужны для первого вертикального сценария. Нынешний Keychain `WhenUnlockedThisDeviceOnly` сохраняется; не снижать protection ради фонового polling (`Security/KeychainStore.swift:16–24`).

P0→P1/P2→P3→P4→P5 интеграция→P6. Макеты P5 можно делать после freeze модели; live стадии не обходят P0. Пользователь подтвердил отсутствие данных и production: **не делаем миграции, legacy_manual, dual-read или параллельный API v1**. Переписываем модель/хранение/контракт под новый сценарий; пригодные проверки безопасности и атомарности используем повторно, не переписываем всё ради переписывания. Тестовые fixtures пересоздаём под новый формат; старые и неизвестные backup-форматы отвергаем явно, без конвертера. Новый backup поддерживает round-trip только новой схемы. Сброс относится только к явно идентифицированному тестовому каталогу приложения при реализации, не к budget ledger, credentials, отчётам или пользовательским файлам; в этой плановой правке ничего не удаляется. Restore не отправляет чужие remote IDs/tokens и не возрождает tombstone: восстановленные данные сначала локальные, облачная отправка отдельным действием.

## 10. Acceptance и проверка

Стартовый eval можно выполнить на меньшем наборе до A13, но это не итоговый gate. Сначала проверить качество upload-профиля на реальных тканях/белом фоне/тонких деталях, затем фиксировать лимиты. Контроль времени и цены ingestion: до live запуска выбрать числовой SLA и лимит задачи исходя из разрешённого провайдера; пока они неизвестны, live gate закрыт. Бюджет не расширяется числом тестовых фото.

## 11. Риски и точки остановки

- Работающий segmentation/vision/embedding/scoring provider ещё не доказан. Нельзя заменить весь AI правилами и объявить MVP готовым.
- Похожесть может не давать хороших луков: P0/P4 quality eval должен сравнить подходы; не инвестировать в vector DB до проверки гипотезы.
- Дорогое O(N²) AI и пересчёты: batch/candidate bounds, debounce/revision coalescing, task budget; не обещать все пары за фиксированную цену без измерений.
- Новое storage/backup: тесты атомарности и восстановления при сбоях; неиспользуемые активы GC только после атомарной активации и отсутствия ссылок/leases. Это безопасность новой схемы, не перенос данных старого прототипа.
- Серверное хранение — новая privacy boundary: личные фото запрещены до согласованной политики и operational readiness.
- CoreSimulator restriction остаётся: использовать разрешённый host runner/Xcode, не обход sandbox. 26 core tests не заменяют UI tests.

**Стоп текущей плановой стадии:** план и независимая архитектурная проверка сохранены; приложение/сервисы впоследствии удалены по запросу пользователя. Следующая исполнимая стадия — P0 (ADR/контракт/feasibility), затем управляемое обновление Ultragoal, не продолжение старого M2 как будто архитектура прежняя.

## Независимая проверка плана

Architect `/root/ingestion_arch`: **APPROVE_WITH_OPEN_GATES** после исправления стабильного operationID при обновлении pipeline и серверной семантики отзыва согласия. A2/A16 обновлены. Одобрение относится только к переходу к P0; provider, retention/лимиты/бюджет, реальное качество и native runtime не закрыты. Проверка read-only, не тестирование реализации.
