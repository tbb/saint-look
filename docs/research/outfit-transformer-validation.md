29 октября 2026. Проверены реальные веса и 16 публичных фотографий, реализован
изолированный fp32 адаптер. HTTP-пайплайн, iOS и полная готовность вещи этим

`missing_keys`, `unexpected_keys`, `mismatched_keys`, `error_msgs` пусты.
Все URL/хеши сохранены в [manifest артефактов](../../backend/ml/assets.json).

Используется `BertModel.pooler_output`768D, а не Dense/Normalize из оболочки
SentenceTransformer: именно так написан Feature Extraction исходной card.
ResNet даёт512D; обученные проекции512→64 и768→64 соединяются в128D.
Все модули `eval`, `requires_grad=False`, вычисления `inference_mode`, fp32 CPU.
Никакого случайного адаптера или fallback нет.

Вход — настоящая фотография вещи. Выбран исходник: подготовка представлений
не зависит от sandbox-водяного знака и не ждёт генерацию иллюстрации. Это выбор
зависимостей и воспроизводимости, а не доказанное преимущество качества перед
вырезкой. После EXIF transpose используются RGB, bilinear224×224 без crop,
ImageNet mean/std как в опубликованном примере. EXIF transpose явно версионирован
как наша подготовка; на этом наборе численные представления повторяются точно.
Текст воспроизводимо строится из актуальных ID типа и отсортированных уникальных
цветов. Например `shirt. Colors: black, white.`; JEV дополнительно не вызывается.

## Метрика и границы утверждений

В `model.py` query L2-нормализован, `encode_single_item` возвращает ненормализованный
concat. Нормы реальных item-векторов7.44…12.13 — единичными они не являются.
Наш envelope хранит их **без нормализации**. Конкретный опубликованный inference
пример в README задаёт `torch.cosine_similarity(predicted_embedding, item_database)`.
Адаптер использует этот cosine только при scoring.

Отдельного training/evaluation script в закреплённом HF дереве нет: README
показывает loss через `pos_dist/neg_dist`, но определения расстояния нет. Поэтому
метрики FITB/MRR из card **не воспроизведены**, а cosine обозначен как опубликованный
пример inference, не доказанная training metric. Сравнение dot/cosine/negative
Euclidean сохранено в JSON: они дают разные ранги. Например, при пустом контексте
cosine начинает с black-jeans, dot с creepers; при контексте8 cosine top3 —
pub-15/white-tee/light-polo, dot — pub-15/pub-30/creepers. Эти нефильтрованные ранги
проверяют арифметику, не являются допустимым продуктовым подбором категории.

Сравнение адаптера с оригинальным `model.py` по контекстам0/1/3/8/16 дало
максимальную ошибку0. Padding не изменил query; перестановка контекста дала
максимум порядка6e-8. Повтор подготовки первой вещи побитно совпал.
Все векторы/score конечны; query norm≈1. В config `max_items=8` —16 проверено
только технически, вне указанной длины обучения. Пустой learned query вычислим,
но модель не обучает нашу стратегию сборки полного лука. Target category и
whole-outfit score у этого head отсутствуют: категории и сборка0…N относятся
к продуктовой логике следующих задач.

## Набор и измерения

16 вещей:8 body,4 bottom,4 shoes; после исключения исходника у низа/обуви остаются
по3 альтернативы. Старые13 pilot-фото дополнены olive-cargo, black-jeans, creepers.
Это development-набор, не holdout; человеческих вкусовых оценок нет. Реальные
публичные фото и их атрибуция сохранены в JSON. Manifest локального набора:
`/tmp/saint-look-epic63-public-v1/manifest.json`, SHA-256
`5d85dde081e8d90421e72b0aa00367aa33151e6ba32ded5e6756999e0644bbf6`.
Исходники/лицензии для нового набора ведёт UI/UX-исполнитель #73.

Среда: Linux x86_64, Intel Xeon Cascadelake,4 logical CPU, около5.8GiB RAM,
Python3.12.14, torch2.6.0+cpu, torchvision0.21.0+cpu, transformers4.49.0,
Pillow11.1.0, numpy2.2.3, safetensors0.5.3. Точные версии проверяются при старте.
CPU shared characteristics Fly этим не воспроизводятся.

Основной прогон с2torch threads:

| Измерение | Факт |
| --- | --- |
| Head startup, включая import | 2.37с |
| Первая подготовка, включая lazy import/load/hash всего encoder | 11.69с |

Все веса скачаны заранее; cold означает холодный процесс/encoder, **не очищенный
page cache ОС**. mmap safetensors затрагивает страницы по мере использования;
размер файла1.88GB не равен RSS. Разные запускаемые процессы показали примерно
894–925MiB peak RSS; это не гарантия верхней границы при других текстах/изображениях.

Вызов `rank` включает валидацию envelopes, tensor creation, query и300 сравнений.
Для нагрузки300 векторы16 вещей повторены: синтетика только для объёма вычисления,
не300 разных вещей и не тест вкуса. Медианы30 повторов:

| Контекст | rank300, мс | максимум, мс |
| --- | ---: | ---: |
| 0 | 14.19 | 16.62 |
| 1 | 13.67 | 15.40 |
| 3 | 14.41 | 14.91 |

Эти числа исключают передачу данных, HTTP и отображение. Цель примерно2сек

подбор во время cold prepare может ждать. Это надо измерить в интеграции.

## Память всей группы при лимите1GiB

Отдельный локальный systemd user unit: `MemoryMax=1G`, `MemorySwapMax=0`,
1torch thread. Внутри — настоящий idle Node24.21 backend, существующий fixture
provider отдельным процессом,16 фото и проверка модели. Веса скопированы в свежие
файлы внутри группы для учёта их page cache. Общий лимит хоста не изменялся.
[Сохранённые kernel counters](outfit-transformer-memory.json):

- `memory.peak=925290496`байт (882.4MiB);
- `memory.events`: max/oom/oom_kill/oom_group_kill=0;
- exit0, backend и fixture оставались живы; benchmark23.31с;
- с1потоком первая подготовка13.65с; следующие0.196–0.253с, медиана0.218с;
  медианы rank300 для контекстов0/1/3/8/16:13.45/13.96/14.16/14.75/17.60мс;
- сумма RSS процессов достигла1092944KiB; общие страницы здесь считаются повторно.

Первый запуск группы не стартовал Node из-за PATH у systemd; исправлен абсолютный
путь. Это инфраструктурный отказ до inference, не OOM и не повтор до случайного
зелёного результата. Финальная строка systemd после освобождения группы показала
другой memory peak; отчёт использует kernel `memory.peak/events`, прочитанные,
пока группа и backend ещё существовали.

Успех ограниченного локального прогона не доказывает запас1GB Fly: файлы библиотек
могут разделять страницы с хостом, ОС находится вне unit, HTTP-пайплайн изображений
был idle. Требуется измерить окончательный контейнер и конкурентные операции на
целевой машине. Преждевременный вывод о необходимости платного расширения также
не делаем. Возможный следующий вариант — та же fp32 mmap модель и один worker
на существующей машине, только после проверки реального memory peak/задержки;
если запаса нет, конкретный размер/стоимость согласовать отдельно. Quantization
и новые платные мощности этим результатом не разрешены и не выполнялись.

## Проверка1GiB с работающим HTTP-пайплайном

После idle-прогона проверена конкретная оставшаяся гипотеза: помещается ли
обработкаPNG/JSON/base64 одновременно с encoder. В той же модели/версии и при
1torch thread проведены16 prepare и16 настоящих HTTP ingestion+illustration,
максимум2 одновременно, внешние провайдеры — существующие loopback fixtures.
Все16 изображений загружены/декодированы, результаты прочитаны по HTTP.
Контрольные ответы не выдаются за настоящие изображения внешнегоAI.

[Kernel counters и времена](outfit-transformer-pipeline-memory.json):

- exit0, все16 pipeline и16 encoder завершены; OOM/oom_kill0;
- memory.peak1073991680байт при memory.max1073741824, swap0;
- memory.events.max5085: лимит реально срабатывал, ядро освобождало память;
- summed RSS1403760KiB с повторным учётом shared pages;
- elapsed32.67с; первая cold prepare14,59с;
- counts16attributes/16cutout/16illustrationPreparation/16illustrationAttributes/16generation.

Первый HTTP-прогон дал400: испытательный код отправил JPEG в endpoint
иллюстраций, тогда как его действующий контракт требует PNG. Это ошибка
испытательного запроса, не модели/продукта. После исправления формата на PNG
(как делает iOS) выполнен один указанный прогон. Никакие проверки backend
не ослаблялись. Размеры/хеши фотографий для encoder остались прежними.

**Вывод уточнён:** запас1GB не подтверждён, рабочая нагрузка достигла лимита.
Факт отсутствия OOM на16 фото не разрешает считать конфигурацию подходящей.
Перед настоящим выпуском нужен обоснованный выбор: измеренная оптимизация
без изменения модели либо отдельное согласование большего объёма памяти;
финальные условия всё равно проверяются на Fly. Новые мощности не создавались.

Воспроизведение проверки модели из нового clone описано в README адаптера:
`fetch_assets.py` плюс `fetch_public_dataset.py`, затем `validate_real.py`.
Совместный замер памяти использует сохранённый `measure_pipeline.py`; команды
systemd1/2GiB, версии и условия pagecache приведены в README.
Все16 исходников/преобразований перепроверены с Pillow11.1.0 и13.0.0, SHA
совпадают. Reference model.py скачивается по фиксированному revision и hash.

## Сравнение с локальным лимитом2GiB

По той же нагрузке и с тем же1потоком выполнен один сравнительный прогон,
изменён только лимит unit на2GiB (и новая временная БД для тех же16 вещей).
[Точный результат](outfit-transformer-pipeline-memory-2g.json): все16encoder
и16HTTPпайплайнов завершены, peak1081884672байт (~1031.8MiB),
memory.events.max/oom/oom_kill0. Elapsed31.88с против32.67с при1GiB.
Первыйprepare14,18с, остальные0,217–0,307с. Малое различие времени не выдаётся за доказанное ускорение:
один прогон каждого размера, pagecache тёплый, фоновые процессы могут влиять.
Изолированное изменение лимита устранило memory-limit events и дало запас
для этой нагрузки без сменыfp32модели.

Оркестратор независимо прочитал действующую Fly machine `d8d9643dc953d8`, AMS,
shared1CPU/1024MB: MemTotal987884KiB, MemAvailable777092KiB, swap0 при idlebackend.
Это snapshot свободной памяти **до** установки модели, не замер модели наFly.
Даже локальный idlecombinedpeak882MiB превышает этот доступный объём.
Следовательно, конкретный кандидат для согласования — существующая машина
с2GBRAM при прежнихCPU/диске, без новых машин; перед выпуском измерить её
реальный пик и запросы. Изменение тарифа/конфигурации требует отдельного
разрешения владельца и этим отчётом не выполнено.
