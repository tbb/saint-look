# Нативная замена длинного названия лука (#53)

Статус: явный пункт edit menu **Select All** прошёл пять заранее ограниченных целевых проверок. Полный PR CI выявил два других visual failure; синхронизация завершения первоначального ввода прошла три заранее ограниченных целевых проверки. Диагностика iPad и полный CI финального варианта ещё не завершены.

Все сценарии используют Simulator, локальный управляемый backend и тестовый гардероб. Настоящие AI API, production-секреты и пользовательские вещи не задействованы. Среда целевого прогона: Xcode 26.6 (17F113), iPhone 17 Pro, iOS 26.4, `iphone-max-text` / accessibility-extra-extra-extra-large.

## Исходная ошибка и точный контракт

В [исходном visual job](https://github.com/tbb/saint-look/actions/runs/40587461072/job/122484261623) 27 октября 2026 в 22:06:14 UTC после triple tap и ввода «Черновик» получилось «Черновик по осеннему городу после работы». Exact assertion сработала **до Done и сохранения**. Общий CI отменили позднее; это не отменяет зафиксированный failure. iOS-код совпадал с main 3a000705; fitting-изменения его не меняли.

Тестовое действие должно заменять всё название. Фактически заменилось только первое слово. Сам результат не доказывает внутреннюю причину UIKit, потерю третьего касания или зависимость от Dynamic Type/горизонтальной прокрутки. Код приложения использует обычный TextField с binding; сохранение на момент ошибки ещё не вызывалось.

Новый `testNativeLongOutfitNameReplacement` проходит через UI: ready-four → Луки → создать лук из body+bottom → сохранить «Прогулка по осеннему городу после работы» → открыть editor → заменить на «Черновик» → сохранить → снова открыть. Проверяется точное значение до Done, в detail, коллекции и повторно открытом editor, а также отсутствие новых ingestion/provider-запросов. Это однократный сценарий в обычном visual suite.

## Что показал UIKit trace

Временный таймер каждые 100 мс читал исходный UITextField: identity, firstResponder, длину UTF-16, selectedTextRange, markedText, язык клавиатуры и frame. Логировал только изменения, без текста. Он не менял binding/focus/selection, не добавлял SwiftUI views/modifiers; observer effect всё же возможен.

В `name-range.log` из artifacts 40604878750:

- Первый проход, строки 121–124: после focus caret 8..8, length 40; после Cmd+A в 00:00:01.593 UTC появился range 0..40; после typeText длина стала 8.
- Второй проход, строки 231–234: после focus в 00:02:23.141 остался caret 8..8. Cmd+A синтезирован около 00:02:26; полного диапазона до typeText trace не обнаружил. Ввод увеличил длину 40 → 44 → 48 и caret 8 → 12 → 16.
- В обоих интервалах сохранялись identity исходного поля, firstResponder=true, en-US и markedText=false. Frame переместился с y=368.667 на y=144 при вводе.

Наблюдение поддерживает отсутствие сохраняющегося полного выделения после shortcut во втором проходе. Оно не подтверждает refocus/recreation или смену языка в этом интервале и не объясняет внутреннюю причину недействующей команды. Состояния короче 100 мс не исключены. Raw events также адресованы одному app PID, с modifiers=16 у Cmd+A и modifiers=0 у следующего typeText; это не доказательство доставки команды.

## Исправление тестового действия: явная команда edit menu

Вместо предположения о результате multi-tap или shortcut helper выполняет tap по уже сфокусированному insertion point, затем ищет native **Select All / Выбрать всё** как menu item/button. Команда должна существовать, быть hittable и enabled. Большой Dynamic Type может разбивать меню на страницы: обход ограничен тремя страницами через видимую enabled-кнопку Forward. Отсутствие команды завершает тест с PNG/AX; альтернативных gestures, keyboard fallback, удаления символов и прямой мутации состояния нет.

Проверка [32365bb / 40606532275](https://github.com/tbb/saint-look/actions/runs/40606532275) заранее ограничена пятью итерациями, без `retry-on-failure` и `run-until-success`. Фактически все пять прошли: 204.162 / 190.174 / 198.966 / 176.506 / 205.798 с; итог XCTest — **5 tests, 0 failures**, 975.605 с. В каждом проходе log содержит native Tap Forward → Tap Select All. Trace подтверждает range 0..40 после команды, затем length 8 после ввода; строки 125/255/386/494/602 в `name-range.log`. Все exact-name, save/reopen и provider-count assertions выполнены. Trace оставляли только для измерения, поэтому полный прогон финального варианта без него остаётся обязательным.

Cleanup f3269a6 восстанавливает app-файлы и scripts к main 3a000705 и удаляет trace environment. В итоговом коде остаются только menu helper и регрессионный UI-сценарий. Первый обычный PR CI проверил этот cleanup со всеми visual profiles, без временного selector, повторов и trace; он завершился ошибкой, подробности ниже. Два независимых ревью cleanup не нашли нарушений standards или конкретных code defects; runtime-проверка финального head не заменяется этими ревью.

Исходный полный visual journey и все exact assertions сохраняются. Отдельный Save failure не скрывается успешной заменой текста. Эта работа поддерживает дальнейшие проверки #43; #44 / PR #52 уже вмерджен. Она не оценивает качество стилизации и не разрешает реальные provider-вызовы из #45.

## Полный PR CI и завершение первоначального ввода

[PR CI 40609278356](https://github.com/tbb/saint-look/actions/runs/40609278356), head 3565379 / merge ref 468ee2a, выполнил все четыре visual profiles. По отдельным test events: **7 passed, 2 failed, 3 штатных skips**. В iphone-light прошли все три сценария; в iphone-dark — два основных; в iphone-max-text прошёл PublicPhotoJourney, но упал первоначальный ввод в focused regression; в ipad-light прошёл focused regression, но PublicPhotoJourney упал на переходе к вкладке «Гардероб». SecondaryStates штатно запускается только в iphone-light. Частичные summaries после перезапуска runner не включают ранний failure, поэтому не заменяют подсчёт событий.

Первый visual failure, 28 октября в 01:13:00 UTC: после `typeText` в ещё пустое поле exact assertion прочитала «Прогу» вместо длинного названия. До Select All, Done и сохранения тест не дошёл. Native failure-count check прошла. Raw event `40DA516A-AE3E-442F-975D-0D06A353068E` содержит всю ожидаемую строку (40 UTF-16), modifiers=0 и target PID 73741. `typeText` начался на t=106.48, synth на 106.76, idle на 107.66, чтение value на 108.00.

Видео `B5C2924F-293C-4556-9DB0-8850B71323D9.mp4` в [visual artifacts](https://github.com/tbb/saint-look/actions/runs/40609278356/artifacts/12785752388), каталог `UITests-20261028T011026Z`, показывает продолжение ввода: кадр 106.5 с — пустое поле с caret и клавиатурой; 108.5 с — текст дошёл до «…огулка по осенн…»; 109.7 с — виден конец «…у после работы». Из-за горизонтального скролла последний кадр не доказывает полное точное значение, но показывает, что ввод не остановился на «Прогу» после раннего чтения.

Поэтому helper теперь после единственного `typeText` ожидает **точное полное value** максимум 15 с, затем выполняет исходную exact assertion перед Done. Никакого повторного ввода, Paste или изменения binding нет. Если значение остаётся усечённым либо содержит старый текст, ожидание завершается ошибкой с PNG/AX. Весь UI-путь создания, замены, сохранения и повторного открытия сохранён. Узкий эксперимент [5dda36b / 40618398669](https://github.com/tbb/saint-look/actions/runs/40618398669) заранее ограничен тремя итерациями iphone-max-text, без app trace, повторного ввода и retry-on-failure. Фактически все три прошли: 231.033 / 142.955 / 178.478 с; итог XCTest — **3 tests, 0 failures**, 552.467 с. Проверены первоначальный полный ввод, замена, точное значение до Done, сохранение и повторное открытие. Временные selector и iterations находятся только в отдельной диагностической ветке; чистый код d5eb1dd их не содержит. Этот результат не заменяет полный CI финального варианта; он ещё не выполнен, а iPad-диагностика остаётся незавершённой.

Отдельный iPad failure произошёл после успешного Back из «Лук» в «Луки»: `waitVisible` не завершился для верхней вкладки `tshirt` / «Гардероб». AX и screenshot показывают видимую вкладку и две native Button-репрезентации, но конкретный false-subcondition и причина пока не установлены. `selectTab`/`waitVisible` этим исправлением не меняются. Кроме того, outfits suite в том же CI получил `processing_unknown` на первой тестовой вещи ещё до конструктора; отдельная диагностика — #55. Эти failures не объявляются исправленными или доказанными инфраструктурными сбоями.
