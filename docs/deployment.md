# Fly.io dev: деплой и откат

Стенд #9 запускает один backend с фоновой обработкой и управляемыми HTTP-ответами провайдеров внутри контейнера. `/health` и результаты обозначены `demo`; реальные AI API не используются. SQLite и временные файлы лежат на volume `/data`. Небольшой простой при redeploy допустим. Snapshots отключены; volume нельзя удалять ради отката кода.

## Аккаунт и бюджет

25 октября 2026 CLI авторизован, платёжный источник подтверждён (`CURRENT`, `billable=true`). Создано приложение `saint-look-dev-tbb` с зашифрованным volume `saint_look_data` 3 GB в AMS. Scheduled snapshots выключены, сохранённых снимков нет. Выделены shared IPv4 и IPv6, секрет владельца staged, app-scoped deploy token и переменные GitHub Actions настроены. Машин пока нет; адрес `https://saint-look-dev-tbb.fly.dev` станет рабочим после первого успешного deploy.

Пользователь согласовал одну shared CPU машину с 1 GB RAM и диском 3 GB за ориентировочные $7–9/месяц **плюс трафик и налоги, без автоматической остановки на $10**. Это явно заменяет прежнее требование общего hard cap для dev в [ADR-0002](adr/0002-managed-dev-hosting.md). У Fly нет встроенных billing alerts. `FLY_BUDGET_VERIFIED=true` фиксирует подтверждённую оплату и согласованный режим расходов, но не ограничивает счёт. Перед созданием других ресурсов или увеличением конфигурации нужен отдельный пересмотр бюджета. Текущий диск оплачивается и без работающей машины. [Сравнение платформ](research/hosting-alternatives.md), [цены](https://fly.io/pricing/), [контроль расходов](https://docs.fly.io/about/cost-management).

Free trial не считается постоянным стендом: опубликованный лимит — 2 VM-часа или 7 дней, а trial-машины автоматически останавливаются через 5 минут. Добавление карты завершает trial и включает платную тарификацию. Фактическую доступность trial для аккаунта нужно проверить отдельно. [Правила trial](https://docs.fly.io/about/free-trial).

## Однократная настройка после допуска

Создайте отдельное Fly App в нужной организации без автоматической выкладки из GitHub. Для подготовленной конфигурации используется регион `ams`, одна машина shared CPU / 1024 MB и существующий volume `saint_look_data` размером 3 GB в том же регионе. Volume монтируется в `/data`; scheduled snapshots должны быть отключены. Не включайте autoextend, autoscaling, резервную машину, выделенный IPv4 или платный remote builder. Для HTTPS используется адрес приложения и shared IPv4. `fly.toml` задаёт порт 8080, health `/health`, SIGTERM с 15 секундами на завершение; выключен autostop, чтобы фоновая очередь продолжала работать без входящих запросов.

Задайте секрет `SAINT_LOOK_OWNER_TOKEN` длиной не менее 32 символов через безопасный ввод CLI, не через аргумент с открытым значением. Он должен совпадать с GitHub secret ниже. Ключи AI-провайдеров не нужны. Создайте deploy token, ограниченный этим приложением, с конечным сроком жизни; личный токен CLI в GitHub не переносится. Для текущего токена задан срок 2160 часов (90 дней) от 25 октября 2026; перед истечением обновите GitHub secret `FLY_API_TOKEN` новым app-scoped токеном.

В Repository → Settings → Secrets and variables → Actions настройте:

| Вид | Имя | Значение |
| --- | --- | --- |
| Secret | `FLY_API_TOKEN` | Deploy token только этого приложения |
| Secret | `SAINT_LOOK_DEV_OWNER_TOKEN` | Тот же токен владельца, что в backend |
| Variable | `FLY_APP_NAME` | Точное имя выделенного существующего приложения |
| Variable | `SAINT_LOOK_DEV_URL` | HTTPS origin без пути, query, fragment и credentials |
| Variable | `FLY_BUDGET_VERIFIED` | `true` только после проверки оплаты и согласования контроля расходов |
| Variable | `ACTIONS_BUDGET_VERIFIED` | Для private repository: после проверки бюджета Actions |

Все jobs сохраняют бюджетный guard до выделения runner. Зелёный run с пропущенными jobs не является деплоем. Токены передаются через environment; не публикуйте удалённые `.xcresult` с диагностикой окружения. Workflow сохраняет только MP4 синтетического сценария.

## Первый и последующие деплои

1. Влейте конфигурацию #9 в `main` и дождитесь успешного **push CI на точном merge SHA**: jobs `changes`, `backend`, `ios`, `container`, `deploy-policy`. PR CI и ручной CI этого не заменяют.
2. Запустите ручной deploy workflow из branch **main**, указав полный 40-символьный SHA и operation `deploy`. Один workflow сериализует выкладки; новый run не отменяет текущий.
3. Проверка допуска подтверждает историю main и происхождение CI. Из выбранного коммита создаётся чистый `git archive` с совместимым `backend/release.json`; symlinks отклоняются. В архив добавляется `backend/REVISION`. Workflow и конфигурация хостинга берутся из доверенного checkout main. Перед сборкой текущий доверенный `fly.toml` копируется внутрь архива поверх исторического: Fly разрешает путь к Dockerfile относительно конфигурации, поэтому и Dockerfile, и Docker context остаются из выбранного коммита. Таким образом, к архиву добавляются встроенный SHA и текущая конфигурация эксплуатации.
4. Pinned `flyctl 0.4.122` собирает Docker локально на GitHub runner и загружает образ в Fly. Перед deploy проверяются существующий volume и число машин; чужая или расширенная конфигурация должна быть отклонена. Выкладка не создаёт дополнительную HA-машину. При неоднозначной ошибке сначала проверьте состояние приложения, затем решайте о повторном запуске.
5. Каждой попытке выкладки назначается свежий UUID `SAINT_LOOK_DEPLOYMENT_ID`. Backend возвращает его как `deploymentId`. Это **наш маркер выкладки**, не native Fly Machine/instance ID. `/health` должен показать точные SHA и маркер, `mode=demo`, `dataVersion=1`; прежний процесс с тем же SHA проверку не пройдёт. Успешный выход CLI сам по себе не заменяет HTTP smoke.
6. API smoke выполняет upload → status → PNG → acknowledgement → удаление синтетической вещи. Затем отдельный macOS job запускает Simulator напрямую через HTTPS, проверяет карточку и её сохранность после офлайн-перезапуска. Видео `remote-simulator-ui-video` хранится 7 дней.

После неуспешного health/API/UI шага автоматического отката нет. Не удаляйте volume; ошибка Simulator после успешного API smoke означает неполную проверку сквозного пути.

## Сохранность volume и откат версии

Откат — запуск того же workflow с operation `rollback` и предыдущим совместимым SHA. Данные остаются текущими; operation служит явной пометкой, проверки и путь деплоя одинаковы. Для реальной проверки нужны **два совместимых SHA из main с успешным push CI**. Старые коммиты до release manifest нельзя использовать как первый rollback target. Пока второй совместимой версии нет, откат на другую версию ещё не проверен.

`release.json` объявляет формат данных 1. Backend проверяет SQLite `user_version` до изменений схемы и запуска очереди. Неизвестный будущий формат останавливает процесс: такой rollback считается неуспешным. Не меняйте `user_version` вручную и не подменяйте manifest для обхода проверки. Нужна совместимая версия приложения либо отдельная согласованная миграция; процедура восстановления данных здесь не предусмотрена.

Для наблюдаемой проверки результата используйте Node 24 и публичный CLI из доверенного main. Токен прочитайте скрыто; остальные переменные — HTTPS origin и текущие значения `/health`:

```bash
read -rs SAINT_LOOK_DEV_OWNER_TOKEN
export SAINT_LOOK_DEV_OWNER_TOKEN
export SAINT_LOOK_DEV_URL='https://YOUR-DEV-DOMAIN'
export SAINT_LOOK_EXPECTED_REVISION='FULL_CURRENT_SHA'
export SAINT_LOOK_EXPECTED_DEPLOYMENT_ID='CURRENT_DEPLOYMENT_ID'
node scripts/deploy/probe.mjs seed /tmp/saint-look-canary.json
```

`seed` создаёт одну синтетическую вещь, ждёт `ready`, скачивает результат, но оставляет его без подтверждения. Файл содержит только случайные идентификаторы, наблюдаемый статус, SHA-256 результата и идентичность релиза, без фотографии или токена. Он создаётся с правами 0600 и не перезаписывается. Срок хранения результата остаётся 7 дней, поэтому выполните проверку в пределах этого срока.

Последовательно выполните: перезапуск текущего сервиса; redeploy следующего проверенного SHA; rollback предыдущего проверенного SHA. После каждого события дождитесь готовности. После deploy/rollback обновите expected revision и deployment ID на значения нового workflow. Обычный restart сохраняет маркер выкладки; само событие перезапуска подтвердите отдельно временем и результатом команды Fly. Затем выполните:

```bash
node scripts/deploy/probe.mjs verify /tmp/saint-look-canary.json
```

`verify` проверяет ту же вещь, операцию, версию снимка и точные байты PNG по digest; повторной загрузки нет. Сохраните результат команды вместе с обоими SHA, deployment IDs и причиной перезапуска в issue #9. После всей последовательности удалите синтетическую вещь:

```bash
node scripts/deploy/probe.mjs cleanup /tmp/saint-look-canary.json
unset SAINT_LOOK_DEV_OWNER_TOKEN
```

Это доказывает сохранность **наблюдавшегося готового результата**. Это не доказательство того, что операция была pending именно в момент остановки. Сохранность незавершённой очереди отдельно проверяют процессные тесты backend; для удалённого доказательства нужно записать фактически наблюдавшийся pending перед остановкой и завершение той же операции после неё. Без такого наблюдения нельзя отмечать удалённый сценарий очереди выполненным.

## Что ещё требует реального стенда

Локальные CLI/HTTP/process тесты и hosted Docker/Simulator проверяют подготовленный код, но не Fly.io. Приложение, volume, секреты, оплата и бюджетный допуск подготовлены. До первого запуска остаются merge и успешный main push CI. Реальные deploy, сохранность очереди/результатов, rollback и remote Simulator ещё не подтверждены. Issue #9 остаётся открытой.
