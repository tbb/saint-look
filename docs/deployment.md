# Railway dev: деплой и откат

Стенд #9 запускает один backend и управляемые HTTP-ответы провайдеров внутри контейнера. `/health` и результаты обозначены `demo`; настоящие AI-аккаунты не используются. Данные SQLite и файлы лежат на persistent volume `/data`. При redeploy допустим короткий простой. Резервных копий нет; volume нельзя удалять ради отката приложения.

## Однократная настройка

Создайте новый проект Railway Hobby, окружение и один пустой сервис. Не подключайте автоматический GitHub deploy: исходники загружает только ручной workflow. Корень сборки — корень репозитория, конфигурация — `railway.json`, Dockerfile — `backend/Dockerfile`. Подключите volume с mount path `/data`, одну реплику и публичный HTTPS-домен. `railway.json` требует mount `/data`, использует `/health` и даёт процессу 15 секунд на завершение. В сервисе задайте секрет `SAINT_LOOK_OWNER_TOKEN` длиной не менее 32 символов; он должен совпадать с GitHub secret ниже. Ключи AI-провайдеров не нужны. Контейнер принудительно использует контролируемый профиль независимо от случайно добавленных provider-переменных.

Перед запуском подтвердите фактический тариф, лимиты памяти/CPU, volume и расходы аккаунта. Ориентир проекта — около $10 в месяц, но флаг workflow сам по себе расходов не ограничивает. Установите реальные доступные в аккаунте предупреждения и hard limit, проверьте, что они покрывают требуемый бюджет и не конфликтуют с другими проектами. Только после этой проверки выставьте `RAILWAY_BUDGET_VERIFIED=true`. При невозможности подтвердить предел расходов оставьте деплой выключенным. Детали тарифа и ограничения платформы с первичными источниками собраны в [исследовании](research/railway-deployment.md).

В GitHub Repository → Settings → Secrets and variables → Actions настройте:

| Вид | Имя | Значение |
| --- | --- | --- |
| Secret | `RAILWAY_TOKEN` | Project token конкретного окружения Railway; не account token |
| Secret | `SAINT_LOOK_DEV_OWNER_TOKEN` | Тот же токен владельца, что в сервисе |
| Variable | `RAILWAY_PROJECT_ID` | UUID существующего проекта |
| Variable | `RAILWAY_ENVIRONMENT_ID` | UUID существующего окружения |
| Variable | `RAILWAY_SERVICE_ID` | UUID существующего сервиса |
| Variable | `SAINT_LOOK_DEV_URL` | HTTPS origin без пути, query, fragment и credentials |
| Variable | `RAILWAY_BUDGET_VERIFIED` | `true` только после проверки реального бюджета |
| Variable | `ACTIONS_BUDGET_VERIFIED` | Для private repository: `true` только после проверки бюджета Actions |

Все jobs сохраняют бюджетный guard до выделения runner. При отсутствующем подтверждении job пропускается: зелёный run с пропущенными jobs не является выполненным деплоем. Токены передаются через environment, не через аргументы CLI, исходники или артефакты. Не публикуйте `.xcresult` удалённого прогона с диагностикой окружения; workflow публикует только MP4 синтетического сценария.

## Первый и последующие деплои

1. Сначала влейте конфигурацию #9 в `main` и дождитесь успешного **push CI на точном merge SHA**. До этого первый деплой невозможен. PR CI и ручной CI не заменяют push-проверку. Нужны успешные jobs `changes`, `backend`, `ios`, `container`, `deploy-policy`.
2. В Actions откройте **Deploy checked Railway dev release** → Run workflow. Выберите branch **main**, укажите полный 40-символьный SHA из main и operation `deploy`. Один workflow сериализует деплои; новый запуск не отменяет текущий.
3. Workflow проверит принадлежность SHA истории main, происхождение CI и все обязательные jobs. Из коммита создаётся чистый `git archive`; грязные файлы workspace не попадают в релиз. Коммиты без совместимого `backend/release.json` и архивы с symlink отклоняются. В архив добавляется `backend/REVISION` с точным SHA. Логика подготовки и проверки берётся из доверенного workflow main, а не из выбранного старого исходника.
4. Railway CLI **5.71.0** загружает архив с явными project/environment/service ID. `--no-gitignore` применяется только к этому архиву, чтобы включить сгенерированный `REVISION`. `up --detach --json` означает постановку деплоя в очередь, а не готовность. При неоднозначной ошибке загрузки сначала проверьте Railway, прежде чем повторять команду.
5. Проверка ожидает `/health` с точными `revision` **и** `deploymentId`, `mode=demo`, `dataVersion=1`, затем проходит авторизованный upload → status → PNG → acknowledgement → удаление синтетической вещи. Старый процесс даже с тем же SHA не удовлетворит проверку нового deployment ID.
6. Отдельный macOS job запускает Simulator напрямую против HTTPS, проверяет готовую карточку и её сохранность после офлайн-перезапуска. Ссылка на run, SHA и Railway deployment ID — доказательство конкретного запуска. Видео доступно как `remote-simulator-ui-video` 7 дней.

После неуспешного health/API/UI шага автоматического отката нет. Посмотрите статус конкретного deployment в Railway и безопасную диагностику сервиса. Не удаляйте volume и не повторяйте обработку реальных фотографий ради проверки. После успешного API smoke ошибка Simulator означает неполное end-to-end доказательство, даже если backend уже работает.

## Сохранность volume и откат версии

Откат — запуск того же workflow с operation `rollback` и предыдущим совместимым SHA. Данные остаются текущими; operation служит явной пометкой, проверки и путь деплоя одинаковы. Для реальной проверки нужны **два совместимых SHA из main с успешным push CI**. Старые коммиты до release manifest нельзя использовать как первый rollback target. Пока второй совместимой версии нет, откат на другую версию ещё не проверен.

`release.json` объявляет формат данных 1. Backend проверяет SQLite `user_version` до изменений схемы и запуска очереди. Неизвестный будущий формат останавливает процесс: такой rollback считается неуспешным. Не меняйте `user_version` вручную и не подменяйте manifest для обхода проверки. Нужна совместимая версия приложения либо отдельная согласованная миграция; процедура восстановления данных здесь не предусмотрена.

Для наблюдаемой проверки результата используйте Node 24 и публичный CLI из доверенного main. Токен прочитайте скрыто; остальные переменные — HTTPS origin и текущие значения `/health`:

```bash
read -rs SAINT_LOOK_DEV_OWNER_TOKEN
export SAINT_LOOK_DEV_OWNER_TOKEN
export SAINT_LOOK_DEV_URL='https://YOUR-DEV-DOMAIN'
export SAINT_LOOK_EXPECTED_REVISION='FULL_CURRENT_SHA'
export SAINT_LOOK_EXPECTED_DEPLOYMENT_ID='CURRENT_DEPLOYMENT_ID'
node scripts/deploy/probe.mjs seed /tmp/saint-look-canary.json
```

`seed` создаёт одну синтетическую вещь, ждёт `ready`, скачивает результат, но оставляет его без подтверждения. Файл содержит только случайные идентификаторы, наблюдаемый статус, SHA-256 результата и идентичность релиза, без фотографии или токена. Он создаётся с правами 0600 и не перезаписывается. Срок хранения результата остаётся 7 дней, поэтому выполните проверку в пределах этого срока.

Последовательно выполните: перезапуск текущего сервиса; redeploy следующего проверенного SHA; rollback предыдущего проверенного SHA. После каждого события дождитесь готовности, обновите expected revision/deployment ID на **фактически новый** запуск и выполните:

```bash
node scripts/deploy/probe.mjs verify /tmp/saint-look-canary.json
```

`verify` проверяет ту же вещь, операцию, версию снимка и точные байты PNG по digest; повторной загрузки нет. Сохраните результат команды вместе с обоими SHA, deployment IDs и причиной перезапуска в issue #9. После всей последовательности удалите синтетическую вещь:

```bash
node scripts/deploy/probe.mjs cleanup /tmp/saint-look-canary.json
unset SAINT_LOOK_DEV_OWNER_TOKEN
```

Это доказывает сохранность **наблюдавшегося готового результата**. Это не доказательство того, что операция была pending именно в момент остановки. Сохранность незавершённой очереди отдельно проверяют процессные тесты backend; для удалённого доказательства нужно записать фактически наблюдавшийся pending перед остановкой и завершение той же операции после неё. Без такого наблюдения нельзя отмечать удалённый сценарий очереди выполненным.

## Что ещё требует реального стенда

Локальные тесты policy/probe используют временный Git-репозиторий и внешние HTTP-fixtures. Они проверяют отказ непроверенным версиям, идентичность нового deployment, публичный API и протокол проверки сохранности, но не Railway. При подготовке этой реализации аккаунт, бюджет, реальный deploy, volume continuity, rollback и remote Simulator ещё не подтверждены. Успешный обычный CI с пропущенным remote-классом этих подтверждений не заменяет. Issue #9 остаётся открытой до фиксации результатов реального стенда либо явно согласованного переноса оставшейся ручной проверки.
