# Управляемый dev-стенд на Fly.io

25 октября 2026 после приостановки новых регистраций Railway выбран Fly.io: один backend-сервис с фоновой обработкой и постоянным диском. Управляемая платформа позволяет сосредоточиться на сценарии приложения без администрирования VPS; небольшой перерыв при выкладке сервиса с диском допустим для dev-стенда. Локальный запуск сохраняется для разработки; отдельные staging и production на первом этапе не нужны.

Первоначальный выбор Railway заменён после сравнения [альтернатив](../research/hosting-alternatives.md). Форма приложения сохраняется: одна машина, один постоянный диск, ручная выкладка из GitHub Actions. Аккаунт Fly.io подключён; 25 октября 2026 после действий пользователя биллинг подтвердил `CURRENT`. Приложение `saint-look-dev-tbb` работает на одной shared CPU машине с 1 GB RAM и зашифрованным диском 3 GB в AMS. Первая ручная выкладка проверенного коммита `0b4840f` прошла 25 октября 2026; HTTPS API smoke успешен.

## Расходы

25 октября 2026 пользователь согласовал для dev фиксированную конфигурацию: одна shared CPU машина с 1 GB RAM и volume 3 GB, без масштабирования и snapshots. Оценка около $7–9/месяц плюс исходящий трафик и налоги принята **без автоматической остановки при достижении $10**. Это заменяет прежнее требование уведомлений и остановки по общему лимиту для данного dev-стенда; на другие окружения и AI API исключение не распространяется.

Оценка не является потолком счёта. У Fly нет встроенных billing alerts; расход проверяется в кабинете. Workflow проверяет согласованную конфигурацию диска и существующей машины, использует локальную сборку GitHub Actions без платного remote builder и не включает дополнительные машины. Флаг `FLY_BUDGET_VERIFIED` означает проверенную оплату и этот согласованный допуск, а не hard cap. При остановленном backend локальный гардероб остаётся доступен, новая обработка ждёт восстановления; volume продолжает оплачиваться.

## Временные данные

Постоянный диск сохраняет очередь и временные результаты между перезапусками и выкладками. Резервные копии этих серверных данных на первом этапе не создаём: оригиналы и уже доставленные результаты хранятся на клиенте. При потере диска незавершённую обработку потребуется повторить.

Для dev-стенда с публичными тестовыми фото согласовано исключение к сроку физического удаления: результаты становятся просроченными через 7 дней с загрузки, но при остановленном backend файлы могут оставаться на диске до следующего запуска. При запуске просроченные данные очищаются до возобновления обработки и не выдаются клиенту. В работающем сервисе сохраняется более ранняя очистка после подтверждённого сохранения результата на клиенте. Это исключение не переносится автоматически на личные фотографии; независимый от backend механизм удаления для строгого срока в первый этап не входит.
