# Иллюстрации вещей: предварительный HTTP-контракт

Контракт `fitting-square-1024-v1` согласован для реализации #46/#47. Качество
реальной стилизации ещё не подтверждено (#45). По решению владельца от
28 октября 2026 это не блокирует продуктовую реализацию. С 30 октября генератор
подключён к прямому Gemini Interactions API; одной публичной фотографией
подтверждён формат JPEG 1K. Полная реальная подготовка с JEV и Photoroom sandbox
ещё требует проверки. Иллюстрации — отдельный цикл от обычной обработки вещей.

`GET /health` возвращает `illustrationAvailable: boolean`. По умолчанию false:
готовый гардероб продолжает работать, фиктивная иллюстрация не создаётся.
Остальные маршруты требуют существующий bearer владельца.

## Запрос

`POST /v1/items/{itemId}/illustrations`

```json
{
  "operationId": "UUID",
  "photoVersionId": "UUID текущего основного фото",
  "sourceSetVersionId": "UUID набора фото",
  "revision": 1,
  "photos": [{"id": "UUID фото", "role": "front", "imageBase64": "PNG"}],
  "manualType": "Худи",
  "manualColors": ["Чёрный"]
}
```

`revision` — отдельный монотонный счётчик запросов иллюстрации, начиная с 1.
Все UUID возвращаются lowercase. От одного до трёх PNG, до 5 MiB каждый,
весь JSON до 16 MiB, включая base64 оригиналов и подготовленных копий.
Первый снимок — единственный `front`, остальные `back`
или `detail`. Это ракурсы той же вещи, а не разные вещи. Исходники передаются
явно: обычная обработка могла уже очистить временную копию после ack.

Ручные поля необязательны, null равнозначен отсутствию. Тип и цвета — русские
значения `shared/wardrobe-taxonomy.json`; пустой массив ручных цветов допустим.
Повтор того же operationId с тем же содержимым возвращает текущую операцию;
изменение содержания с прежним ID даёт 409 `identity_conflict`.

503 `illustration_unavailable` означает, что запрос не поставлен в очередь.
Новый принятый запрос возвращает 202, повтор — 200.

## Ответ операции

`GET /v1/items/{itemId}/illustrations/{operationId}` и POST возвращают:

```json
{
  "itemId": "UUID", "operationId": "UUID", "photoVersionId": "UUID",
  "sourceSetVersionId": "UUID", "revision": 1,
  "status": "pending", "mode": "live",
  "processing": {"preparation":"pending", "attributes":"pending", "unfolding":"pending", "generation":"pending", "finalization":"pending", "fidelity":"pending"},
  "observedFeatures": null, "effectiveFeatures": null,
  "manualType": null, "manualColors": null,
  "modelVersion": "gemini-3-pro-image",
  "templateVersion": "category-front-anchors-v6",
  "geometryVersion": "fitting-anchors-1024-v6",
  "fittingPoses": null, "preparedSources": [], "resultPath": null, "error": null
}
```

Статус: `pending|ready|failed`. Стадии: `pending|in_flight|done|skipped|failed|unknown|cleared`.
Режим `test` допускается только с локальным HTTP-провайдером при NODE_ENV=test;
для настоящего адаптера режим `live`. Фикстуры не включаются в production.

После JEV оба features имеют форму:

```json
{"version":"fitting-observable-v2-photoroom-sandbox", "type":"Худи", "colors":["Чёрный"],
 "traits":{"silhouette":"relaxed", "body_length":"regular", "sleeves":"long",
 "pattern":"unknown", "pattern_location":"unknown", "pattern_size":"unknown",
 "neckline":"hood", "fastening":"none", "surface":"unknown", "hood":"yes",
 "kangaroo_pocket":"unknown", "patch_pockets":"unknown", "dropped_shoulders":"unknown",
 "contrast_cuffs":"unknown", "lettering":"unknown"}}
```

Неуверенные признаки сохраняются как `unknown`, тип — `Не определён`, цвета —
пустой массив. `effectiveFeatures.type/colors` используют ручные исправления;
наблюдённые признаки не перезаписываются. Новые ручные правки сами запросов не
создают. Клиент сверяет identity, ручные значения и версии перед публикацией.
Наблюдённые цвета отбираются по уверенности JEV: не более пяти основных цветов,
в порядке убывания уверенности; значения ниже порога не добавляются.

`GET .../{operationId}/result` возвращает PNG 1024×1024 с полезным alpha на
полном общем холсте; не обрезать и не центрировать отдельную вещь повторно.
409 `not_ready` — ещё нет результата. `POST .../{operationId}/ack` возвращает
204 только для актуальной готовой операции после надёжной локальной записи
candidate; сервер атомарно фиксирует фото и очищает временные источники и результат.
Клиент публикует candidate только после 204. Повторный ack доставленной операции
безопасен и подтверждает прежний commit; ack устаревшей/удалённой/просроченной
операции возвращает явный отказ. Через семь дней данные также очищаются.
Старый сохранённый клиентский результат остаётся при обновлении или ошибке.
После очистки GET статуса, изображения, подготовленных источников и повторный
POST той же операции возвращают 410 `result_delivered` или `result_expired`.
Очищенная операция не выдаётся как обычный ответ с пустыми признаками: клиент
завершает её доставку и при необходимости создаёт новую явную ревизию.

Готовый ответ содержит `preparedSources: [{photoId, preparedPath}]` для каждого
исходника. `GET /v1/items/{itemId}/illustrations/{operationId}/sources/{photoId}/prepared`
выдаёт точную подготовленную PNG-копию (до 10 MiB, с размерами оригинала).
Клиент надёжно сохраняет **и иллюстрацию, и все подготовленные копии до ack**.
При следующем явном запросе каждый `photos[]` может содержать `preparedBase64`:
так обновление ручных признаков не оплачивает повторную
вырезку уже подготовленных фото. Кэш привязан к неизменному photoId, хешу
оригинала и версиям контракта. Сервер после очистки хранит только хеши этих
копий, а не изображения. Полученный кэш обязан совпасть с ранее выданными
байтами; несовпадение даёт 409 `prepared_source_conflict`. Поле кэша не входит
в fingerprint операции, повторная доставка не создаёт новый запрос.

Суммарный JSON с кэшем всё ещё ограничен 16 MiB. Клиент проверяет полный размер;
нельзя молча отбросить кэш и повторно потратить квоту ради прохождения лимита.
409 `processing_in_progress` означает, что предыдущий запрос для того же
основного фото ещё выполняется: повторить явное действие после завершения.
До первой готовности замена основного фото завершает старую операцию как superseded и не блокирует
запрос новой версии. 409 `processing_unknown` запрещает новую платную попытку
до разбирательства с неизвестным исходом. Ошибка чтения Gemini interaction после
получения receipt (включая 401/403/429) не доказывает отказ генерации и остаётся
unknown.

## Конфигурация и миграция

Реальный путь требует явного `SAINT_LOOK_ILLUSTRATIONS_ENABLED=true`, серверных
`TYPESAFE_API_KEY`, `GEMINI_API_KEY` и выбранного Photoroom-ключа.
`SAINT_LOOK_PHOTOROOM_MODE=sandbox` (по умолчанию) требует `sandbox_…`;
`production` требует `PHOTOROOM_API_KEY` без sandbox-префикса и
`PHOTOROOM_PRODUCTION_APPROVED=true`. В обоих случаях отсутствие подходящего
ключа отключает доступность, без fallback. Этот документ сам по себе не включает
обработку. Цепочка: выбранный Photoroom → JEV → Gemini Nano Banana Pro → тот же Photoroom
для снятия фона у непрозрачного JPEG. Оригинал и подготовленный ракурс идут
отдельными подписанными референсами. Правила подачи референсов v4 описаны ниже.

По разрешению владельца от 1 ноября 2026 `SAINT_LOOK_API_BUDGET_MODE=provider-quota`
в production отменяет внутренние пробные ограничения и ежедневное истечение
допуска, сохраняя журнал и запрет повторных платных вызовов. Режим `trial`
сохраняет прежние строгие проверки политики. `/health` явно возвращает
`photoroomMode` и `apiBudgetMode`; wire-версия признаков
`fitting-observable-v2-photoroom-sandbox` остаётся прежней ради совместимости
существующего клиента и не обозначает фактический billing mode.

Сервер хранит billing mode операции и подготовки исходника, а после очистки —
хеши ранее выданных подготовленных копий. При явном обновлении sandbox-кэш
аутентифицируется, но production заново сегментирует оригинал. Старый кэш не
становится поддельным после сбоя последующей генерации: его receipt сохраняется.
Кэш production повторно используется; неизвестные хеши отклоняются. При удалении
вещи удаляются и эти hash-only receipts. Уже выполнявшаяся операция не меняет
провайдера при рестарте: старые pending-операции другого режима завершаются
`provider_configuration_changed`, неизвестные исходы сохраняют запрет повтора.

CI использует `NODE_ENV=test` и `SAINT_LOOK_ILLUSTRATION_TEST_ORIGIN` с loopback
HTTP. Внешний адрес или отсутствие test-origin при NODE_ENV=test запрещает
доступность. Никакого перехода к реальному провайдеру при ошибке фикстуры нет.
Для нативных тестов `SAINT_LOOK_ILLUSTRATION_TEST_CONTROLLED=true` читает
доступность из локального provider `/health`: `/__control` включает
`illustrationMode: success|failed|unknown`, reset возвращает null/недоступно.

Формат серверных данных 3 мигрирует 1/2, сохраняя вещи и таблицы обработки.
Откат к коду форматов 1/2 запрещён: старый код не соблюдает фиксацию фотографий.
Согласованная публикация и неизменность полного набора после готовности описаны
в [контракте #67](item-publication.md).
Снижение SQLite user_version вручную не является допустимым откатом.

Удаление вещи охватывает все иллюстрации и исходники; tombstone запрещает
воскрешение поздним ответом. Допустимая замена до готовности делает прежнюю операцию
неактуальной. Неизвестный исход внешней операции не повторяется автоматически.

### Gemini trial accounting and recovery

The historical trial reserves $0.40 before each Gemini POST. This is an accounting
estimate, not a provider billing guarantee. The request sets max_output_tokens=2048;
diagnostics in #109 observed an incomplete multi-image response reporting more
output tokens than that setting. The production provider-quota policy relies on
actual provider balance rather than treating this estimate as a hard ceiling. No grounding tools are
enabled. The owner's total API ceiling is $10: the prepared server lifetime cap
is $8.80, leaving $1.20 for three earlier standalone Google probes outside this
ledger. The same-ID $4.50 → $8.80 policy migration preserves every reservation;
the 60/48/24 provider limits and rates stay unchanged. Historical fal reservations
remain in both the total spend and the 24-generation count after migration.
Downgrading the policy to $4.50 is permitted only while the entire reserved cost
fits; older backend budget code cannot accept $8.80 and must not be rolled back
without the compatible policy downgrade or a reviewed budget-code backport.

Gemini uses `store:true` so a saved interaction ID can be recovered with GET.
Google therefore stores the interaction, including uploaded photos. The current
trial uses public photos only; GET recovery does not submit another generation.
Sources: [pricing](https://ai.google.dev/gemini-api/docs/pricing),
[output/thinking cap](https://ai.google.dev/gemini-api/docs/thinking/).

## Посадка по типу вещи — v2

`category-front-anchors-v2` / `fitting-anchors-1024-v2` сохраняют общий квадрат
1024×1024 и координаты манекена. Генератор получает шаблон семейства вещи
(верх, брюки, шорты, юбка, длинная одежда, обувь, головной убор, аксессуары)
с целевым положением. Размеры и координаты проверяет `illustration-layout.mjs`;
после сегментации один равномерный масштаб и перенос регистрируют вещь по шаблону. Поиск границ использует непрозрачные пиксели; всё изображение, включая watermark, преобразуется тем же способом. Части одежды не вырезаются и не растягиваются по независимым осям. Раздельность штанин проверяется до и после размещения; прямоугольник или слитый силуэт не превращаются в брюки геометрическим искажением.

После финальной сегментации непрозрачная вещь должна находиться внутри своей
области с допуском 4% площади непрозрачных пикселей снаружи. Прозрачные края
и полупрозрачный watermark не используются для оценки посадки, но остаются
в PNG. Преобразование, которое обрежет хотя бы один непрозрачный или полупрозрачный пиксель, отклоняется. У длинных брюк дополнительно проверяется расстояние от пояса до щиколоток; слишком широкий силуэт не превращается в укороченные брюки ради попадания в область. Минимальная площадь защищает от почти пустого результата. Это проверка
размещения, а не семантическая гарантия качества вещи.

`illustration_geometry_invalid` означает дефект размещения. В v5 после первого подтверждённого дефекта допускается одна корректирующая генерация; после второго результат не публикуется. `illustration_type_unsupported` просит выбрать известный тип
до генерации; неизвестный тип не расходует резерв Gemini.

Клиент читает сохранённые v1 и v2 пакеты, но на общий манекен накладывает только
v2. Старый результат доступен в карточке; «Обновить посадку» создаёт явную
новую попытку, сохраняя предыдущую публикацию до полного завершения. Кэш
исходной Photoroom-вырезки остаётся пригодным при совпадении сохранённого
хеша; смена шаблона не является причиной повторной сегментации исходника.
Новая вещь всегда сохраняет намерение автоматической подготовки, включая
временную недоступность провайдера, замену неудачного первого снимка и сохранение дополнительных ракурсов до первой готовности. Если предыдущая генерация ещё идёт, новая операция ждёт её завершения; `processing_in_progress` не отменяет обязательную подготовку.

Ограниченная проверка на двух публичных фото: [результаты и границы проверки](../research/fitting-anchors-v2.md).

## Сохранение вещи и посадка — v6

`category-front-anchors-v6` / `fitting-anchors-1024-v6` сохраняют полный квадрат
1024×1024. Генератор редактирует исходную вещь. Серый ориентир задаёт положение
рукавов; ширина корпуса строится по измеренному исходнику. Опорные точки плеч
остаются общими. Измеримый корпус может быть обычным, укороченным или длинным;
неизвестная длина не означает обычную. Финальное размещение — только единый
масштаб и перенос целого PNG, без растягивания по одной оси или отдельных деталей.

Для измеримого корпуса отношение ширины к длине сравнивается с исходником.
Высота капюшона и манжеты ниже подола не входят в длину корпуса худи. Отклонение
более 8% или неоднозначный результат при измеримом исходнике даёт
`illustration_proportions_changed`. Если исходник нельзя уверенно измерить,
численная проверка пропускается; это не подтверждение сохранения пропорций.

### Общая поза лука

Новый манекен имеет фиксированные пропорции и три положения рук: `relaxed`,
`open`, `spread`. Это повороты на 0°, 13°, 34° от прежних рук вокруг плеч
(примерно 11°, 24°, 45° от вертикали); длина рук, корпус и ноги не меняются.
Для каждого PNG сервер проверяет все три положения и возвращает допустимые
в `fittingPoses`. Готовый v6 ответ обязан содержать непустой массив уникальных
значений; отсутствие или неизвестное значение не разрешает клиенту угадать позу.
Метаданные сохраняются атомарно с результатом и его хешем.

Для длинных рукавов проверяются манжеты, расправленность и покрытие полного
контура руки до запястья. Кисть может выходить из манжеты. Для коротких рукавов
направление руки должно пересекать отверстие рукава, а не боковой шов/подмышку.
Низ сохраняет отдельные опорные точки пояса, промежности и щиколоток.

Весь лук использует одну общую позу. Наружный слой имеет приоритет. Внутренний
слой не ограничивает её только когда пиксели его рукавов перекрыты уже показанными
верхними слоями: прозрачная ткань не считается полным перекрытием. Исходные PNG при этом не изменяются и не деформируются. При отображении есть
узкое исключение: короткий рукав внутреннего слоя под явно закрытым (`fastening=none`),
длиннорукавным и непрозрачным верхом ограничивается его наблюдаемым контуром плеч
по строкам изображения. Это только перекрытие в композиции: горловина, центральный
корпус и весь нижний подол остаются. Открытый/неизвестный или полупрозрачный верх
такое перекрытие не разрешает. Правила выбора общей позы не ослабляются. Несовместимые видимые слои показаны
фотографиями отдельно с объяснением. Длинный центральный подол не скрывается
ради выбора позы.

### Расправление сложных исходников

Худи с явно длинными рукавами перед генерацией проходит `unfolding` через
Photoroom Flat Lay (`POST /v2/edit`, `flatLay.mode=ai.auto`). Этот этап расправляет
позу; его результат служит фронтальным ориентиром Gemini. Исходная фотография
остаётся эталоном признаков, измеримых пропорций и финальной проверки идентичности.
Это дополнительный платный запрос обычным Photoroom-ключом, не fal.ai.

Результат расправления сохраняется атомарно с завершением стадии и повторно
используется при единственной корректирующей генерации. Неизвестный исход
расправления останавливает операцию без автоматического повторения. При доставке,
просрочке или замене фото эти временные байты удаляются вместе с остальными.

### Масштаб отображения

Фото без размеров не определяет физический размер вещи. Для короткорукавных
верхов используется минимальная ширина корпуса на манекене: 85 единиц для
приталенного, 105 для прямого/неизвестного, 113 для свободного силуэта (корпус
манекена около 85). Уже достаточно широкую вещь правило не сужает. Масштаб
равномерный: длина растёт вместе с шириной, а низ может оказаться ниже худи
даже при распознанном `body_length=regular`. Явно укороченные вещи исключены.
Это условность отображения, а не прогноз физической посадки. Ограничения плеч,
рукавов, пропорций и полного кадра сохраняются; конфликт завершается ошибкой.

При расправлении худи генератор получает полное расправленное фото, затем три
перекрывающихся фрагмента оригинала (левый, центральный и правый, без изменения
пикселей) и ориентир позы. Фрагменты совместно содержат весь оригинал, включая
принты рукавов, но не задают конкурирующую полную сложенную позу. Финальная
проверка идентичности всегда сравнивает результат с полным исходным фото.

### Проверка качества и повтор

После геометрии независимая проверка Gemini `gemini-3.8-flash` считает рукава и
проверяет дублирование деталей, сложенные рукава и поднятый капюшон. Конкретный
дефект при confidence ≥ 0.9 блокирует публикацию. Затем JEV сравнивает исходник
и результат: крой, принты, материал и конструкцию. Уверенное изменение
(confidence ≥ 0.85) даёт `illustration_identity_changed`. `uncertain` и низкая
уверенность сами по себе не доказывают изменение. Эти модельные проверки не
гарантируют точность всех деталей; геометрия и численные пропорции независимы.

После завершённого результата с ошибкой геометрии, пропорций или идентичности
разрешена одна корректирующая генерация. Подготовленные фото и признаки
переиспользуются. Номер попытки, прежний receipt, хеши и причина фиксируются до
нового запроса. Генерация, структурная проверка, Photoroom и JEV резервируются
раздельно. Неизвестный исход платного запроса, таймаут или отказ провайдера не
запускают коррекцию. После второй ошибки предыдущая полная публикация остаётся.

Оплаченная вырезка сохраняется до локального размещения. Финализированный PNG,
его позы и завершённая стадия сохраняются атомарно до внешних проверок. HTTP
результат недоступен до полной готовности. Рестарт до начала `fidelity` использует
сохранённый PNG; рестарт во время внешней проверки сохраняет unknown без повтора.

### Совместимость

Для новых v6 результатов нужен обновлённый клиент. Старые v2–v4 картинки сохраняют
прежнюю позу, v5 — `open`. Кэш исходной вырезки v2–v5 остаётся пригодным при
совпадении хеша; смена шаблона не оплачивает повторную сегментацию исходника.
Обновление посадки явное, старый пакет остаётся до полной готовности нового.

Худи с v4 и новее использует опущенный капюшон: голова рисуется перед ним,
головной убор — перед головой. Каталог обрезает только пустые поля отдельной
копии; alpha=1 не расширяет миниатюру. Квадрат примерочной остаётся неизменным.
