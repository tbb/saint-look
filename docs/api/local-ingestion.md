# Локальное добавление вещи: контракт v1

Реализовано для [#2](https://github.com/tbb/saint-look/issues/2). Это **demo**: обработчик выдаёт одну синтетическую синюю футболку независимо от фото. Настоящего AI, платных запросов и deployment в этом срезе нет.

## Доступ и идентичность

Базовый URL по умолчанию `http://127.0.0.1:8787`. Все `/v1/*` требуют `Authorization: Bearer <owner-token>`. Один локальный владелец на экземпляр backend; токен задаётся через окружение, в клиенте хранится в Keychain. Это dev-доступ, не многопользовательская авторизация. Сервер привязан к loopback; при будущем внешнем размещении нужен HTTPS. Токен не передаётся через URL. `GET /health` без токена возвращает `{"status":"ok","mode":"demo"}`.

Клиент создаёт три UUID до сети: `itemId` вещи, `operationId` операции и `photoVersionId` снимка. Сервер приводит UUID к нижнему регистру, сохраняет их и возвращает вместе с результатом; клиент принимает только ответ с совпадающими идентификаторами. Полное восстановление операций после сбоя — отдельная задача #4.

## Загрузка

`POST /v1/items`, `Content-Type: application/json`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "imageBase64": "<PNG или JPEG в base64>"
}
```

Одна вещь вне человека, без анкеты. Пара обуви — одна вещь; части комплекта добавляются отдельно. Клиент сначала сохраняет исходник и ожидающую карточку на диске. Для передачи создаёт PNG без метаданных. Backend повторно декодирует и нормализует ориентацию, удаляет метаданные и сохраняет PNG; формат ограничен PNG/JPEG, один кадр, не более 16 млн пикселей, 5 MiB декодированных байтов загрузки и 8 MiB JSON. Неподдерживаемые форматы не передаются обработчику.

`202` означает, что снимок и задание уже записаны в SQLite; обработка идёт независимо от клиента. Повтор тех же трёх идентификаторов и нормализованных пикселей возвращает `200` и текущую карточку. Повтор item/operation с другой идентичностью или изображением — `409 identity_conflict`, существующая запись не меняется.

## Состояние и результат

`GET /v1/items/{itemId}` возвращает `200`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "status": "ready",
  "mode": "demo",
  "type": "Футболка",
  "colors": ["Синий"],
  "resultPath": "/v1/items/62fbcc39-f8b8-4b60-8644-47735bda6810/result",
  "error": null
}
```

В `pending`: `type`, `resultPath`, `error` равны `null`, `colors: []`. В `failed`: `error: "processing_failed"`, тип и результат отсутствуют. Ошибка не создаёт готовую карточку. `GET /v1/items/{itemId}/result` возвращает PNG с прозрачностью только для `ready`; иначе `409 not_ready`. Клиент сохраняет PNG до локального перехода в `ready`; готовая карточка читается без сети после перезапуска.

Ошибки имеют вид `{"error":"code"}`: `400 invalid_identity|invalid_image|invalid_request`, `401 unauthorized`, `404 not_found`, `409 identity_conflict|not_ready`, `413 image_too_large`, `415 unsupported_image|unsupported_content_type`. В ответах и логах нет содержимого фото и токенов. Ответы запрещают HTTP-кэширование.

## Границы среза

SQLite хранит исходник, состояние и результат на локальном диске. Готовый результат переживает перезапуск сервера. Незавершённая запись сохраняется, но после остановки обработчик её автоматически не возобновляет: восстановление — #4. Нет удаления/замены/редактирования, срока хранения и внешнего провайдера; это последующие задачи. Используйте синтетические фото локально. Не разворачивайте этот срез как готовый dev-стенд: инфраструктура и срок удаления относятся к следующим тикетам.
