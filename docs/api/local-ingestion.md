# Локальное добавление вещи: контракт v1

Контракт #2 расширен провайдерами #3 и восстановлением #4. Режим `demo` выдаёт синтетическую футболку; `live` вызывает Gemini и Photoroom после ручного допуска. Управляемый внешний HTTP-транспорт тестов явно обозначается `demo`. Реальные аккаунты и качество API пока не проверены; deployment отсутствует.

## Доступ и идентичность

Базовый URL по умолчанию `http://127.0.0.1:8787`. Все `/v1/*` требуют `Authorization: Bearer <owner-token>`. Один локальный владелец на экземпляр backend; токен задаётся через окружение, в клиенте хранится в Keychain. Это dev-доступ, не многопользовательская авторизация. Сервер привязан к loopback; при будущем внешнем размещении нужен HTTPS. Токен не передаётся через URL. `GET /health` без токена возвращает `{"status":"ok","mode":"demo"}` либо `mode: "live"` в зависимости от конфигурации.

Клиент создаёт три UUID до сети: `itemId` вещи, `operationId` операции и `photoVersionId` снимка. Сервер приводит UUID к нижнему регистру, сохраняет их и возвращает вместе с результатом; клиент принимает только ответ с совпадающими идентификаторами. После отказа связи клиент повторяет отправку с прежними UUID и снимком: уже принятое задание возвращается без нового внешнего вызова.

## Загрузка

`POST /v1/items`, `Content-Type: application/json`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "imageBase64": "<PNG или JPEG в base64>"
}
```

Одна вещь вне человека, без анкеты. Пара обуви — одна вещь; части комплекта добавляются отдельно. Клиент сначала сохраняет исходник и ожидающую карточку на диске. Для передачи создаёт PNG без метаданных. Backend повторно декодирует и нормализует ориентацию, удаляет метаданные и сохраняет PNG; формат ограничен PNG/JPEG, один кадр, не более 16 млн пикселей, 5 MiB декодированных байтов загрузки и 8 MiB JSON. Неподдерживаемые форматы не передаются обработчику.

`202` означает, что снимок и задание уже записаны в SQLite; обработка идёт независимо от клиента. Повтор тех же трёх идентификаторов и нормализованных пикселей возвращает `200` и текущую карточку. Повтор item/operation с другой идентичностью или изображением — `409 identity_conflict`, существующая запись не меняется.

## Состояние и результат

`GET /v1/items/{itemId}` возвращает `200`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "status": "ready",
  "mode": "demo",
  "processing": {"attributes":"done","cutout":"done"},
  "type": "Футболка",
  "colors": ["Синий"],
  "resultPath": "/v1/items/62fbcc39-f8b8-4b60-8644-47735bda6810/result",
  "error": null
}
```

В `pending`: `type`, `resultPath`, `error` равны `null`, `colors: []`. Даже уже полученный тип не выдаётся за полную готовность до проверки вырезки. В `failed`: безопасный `error` из списка ниже, тип и результат отсутствуют. Ошибка не создаёт готовую карточку. `GET /v1/items/{itemId}/result` возвращает PNG с прозрачностью только для `ready`; иначе `409 not_ready`. Клиент сохраняет PNG до локального перехода в `ready`; готовая карточка читается без сети после перезапуска.

Ошибки имеют вид `{"error":"code"}`: `400 invalid_identity|invalid_image|invalid_request`, `401 unauthorized`, `404 not_found`, `409 identity_conflict|not_ready`, `413 image_too_large`, `415 unsupported_image|unsupported_content_type`. В ответах и логах нет содержимого фото и токенов. Ответы запрещают HTTP-кэширование.

## Этапы и ошибки обработки

`processing.attributes` и `processing.cutout` имеют значения `pending`, `in_flight`, `done`, `failed`, `unknown`. Сначала проверяются фото, тип и цвета, затем удаляется фон. Перед внешним вызовом сохраняется `in_flight`, после успешной проверки ответа — `done` вместе с результатом. Перезапуск продолжает только `pending`. Оставшийся `in_flight` превращается в `unknown`, а карточка — в `failed` с `processing_unknown`. Повторный POST не сбрасывает это состояние и не расходует квоту ещё раз. Приложение сохраняет исходник и показывает необходимость разбора результата; автоматического повторного AI-вызова нет.

Коды ошибок обработки:

| Код | Значение |
| --- | --- |
| `provider_not_configured` | Отсутствуют ключи или настройки обработчика некорректны |
| `provider_preflight_required` | Не подтверждены аккаунты, бесплатные квоты и opt-out Photoroom |
| `provider_unauthorized` | Провайдер отказал в доступе |
| `provider_quota_exceeded` | Провайдер сообщил об исчерпании квоты/необходимости оплаты |
| `provider_rejected` | Провайдер явно отклонил запрос |
| `invalid_provider_response` | Ответ неполный, некорректный, слишком большой или не содержит пригодной вырезки |
| `photo_on_person` | Вещь сфотографирована на человеке |
| `photo_multiple_items` | Обнаружены несколько отдельных вещей |
| `photo_no_item` | Вещь не обнаружена |
| `photo_unclear` | Фото неоднозначно для распознавания |
| `inappropriate_photo` | Провайдер не разрешил обработку фото |
| `image_too_large` | Нормализованный PNG превышает предел внешней передачи 5 MiB |
| `processing_unknown` | Запрос мог выполниться; автоматический повтор запрещён |
| `provider_configuration_changed` | Сменился обработчик принятой операции; подмена результата запрещена |
| `processing_failed` | Управляемая ошибка demo |

`mode` сохраняется с операцией и результатом. Backend также различает реальный обработчик, управляемый HTTP-транспорт и синтетический demo внутренним идентификатором, чтобы перезапуск не подменял один другим. Старые готовые карточки #2 остаются доступными, незапущенные demo-задания продолжаются после обновления схемы.
