# Локальное добавление вещи: контракт v1

Контракт #2 расширен провайдерами #3, восстановлением #4, явными повторами/заменой фото #6 и удалением #7. Режим `demo` выдаёт синтетическую футболку; `live` вызывает Gemini и Photoroom после ручного допуска. Управляемый внешний HTTP-транспорт тестов явно обозначается `demo`. Реальные аккаунты и качество API пока не проверены; deployment отсутствует.

## Доступ и идентичность

Базовый URL по умолчанию `http://127.0.0.1:8787`. Все `/v1/*` требуют `Authorization: Bearer <owner-token>`. Один локальный владелец на экземпляр backend; токен задаётся через окружение, в клиенте хранится в Keychain. Это dev-доступ, не многопользовательская авторизация. Сервер привязан к loopback; при будущем внешнем размещении нужен HTTPS. Токен не передаётся через URL. `GET /health` без токена возвращает `{"status":"ok","mode":"demo"}` либо `mode: "live"` в зависимости от конфигурации.

Клиент создаёт три UUID до сети: `itemId` вещи, `operationId` операции и `photoVersionId` снимка. Сервер приводит UUID к нижнему регистру, сохраняет их и возвращает вместе с результатом; клиент принимает только ответ с совпадающими идентификаторами. После отказа связи клиент повторяет отправку с прежними UUID и снимком: уже принятое задание возвращается без нового внешнего вызова. У вещи также есть `revision`: 0 при создании, возрастающее безопасное целое число при явном повторе или замене. Его сохраняет единственный клиент вместе с новой операцией до сети. Это порядок намерений пользователя, а не порядок UUID или прихода HTTP-запросов; мультиустройство не поддерживается.

## Загрузка

`POST /v1/items`, `Content-Type: application/json`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "imageBase64": "<PNG или JPEG в base64>"
}
```

Одна вещь вне человека, без анкеты. Пара обуви — одна вещь; части комплекта добавляются отдельно. Клиент сначала сохраняет исходник и ожидающую карточку на диске. Для передачи создаёт PNG без метаданных. Backend повторно декодирует и нормализует ориентацию, удаляет метаданные и сохраняет PNG; формат ограничен PNG/JPEG, один кадр, не более 16 млн пикселей, 5 MiB декодированных байтов загрузки и 8 MiB JSON. Неподдерживаемые форматы не передаются обработчику.

`202` означает, что снимок и задание уже записаны в SQLite; обработка идёт независимо от клиента. Повтор тех же трёх идентификаторов и нормализованных пикселей возвращает `200` и текущую карточку. Повтор item/operation с другой идентичностью или изображением — `409 identity_conflict`, существующая запись не меняется.

## Явный повтор и замена фото

`POST /v1/items/{itemId}/attempts` принимает те же поля загрузки и два дополнительных: `action: "retry" | "replace"`, `revision` от 1 до `Number.MAX_SAFE_INTEGER`. `itemId` в пути и теле совпадают. Повтор создаёт новый `operationId`, сохраняя локальные `photoVersionId` и нормализованный снимок клиента. Замена создаёт также новый `photoVersionId`, который ещё не использовался для этой вещи. Все остальные ограничения загрузки и авторизации сохраняются.

Новая ревизия должна быть больше принятой. Пропуски разрешены: последняя из нескольких офлайн-замен может прийти первой, даже если backend ещё не видел вещь. Более старая доставка получает `409 stale_revision`; она не меняет актуальную карточку и не вызывает провайдера. UUID операции, ревизия, действие и хеш нормализованного снимка записываются в журнал приёма атомарно с новой текущей попыткой.

Повтор текущей принятой операции возвращает `200`; повтор той же уже вытесненной операции — `409 operation_superseded`. Конфликт идентичности/снимка — `409 identity_conflict`. Если версия снимка уже принималась, повтор разрешён только для текущей версии с прежними пикселями; историческую версию нельзя активировать заново даже с большей ревизией. Если предшествующая замена была отклонена до приёма (например, `401`), явный повтор может впервые доставить эту ещё неизвестную серверу версию локального снимка. У неё остаётся новая большая ревизия, поэтому отложенный запрос замены не вернёт прежнюю операцию. Повтор не включается автоматически из-за квоты, таймаута или неизвестного исхода; требуется новое явное действие пользователя.

## Состояние и результат

`GET /v1/items/{itemId}` возвращает `200`:

```json
{
  "itemId": "62fbcc39-f8b8-4b60-8644-47735bda6810",
  "operationId": "8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534",
  "photoVersionId": "5ba1b8be-51e9-4233-80ee-e6c05523cdc2",
  "revision": 0,
  "status": "ready",
  "mode": "demo",
  "processing": {"attributes":"done","cutout":"done"},
  "type": "Футболка",
  "colors": ["Синий"],
  "resultPath": "/v1/items/62fbcc39-f8b8-4b60-8644-47735bda6810/operations/8b662e4d-2c49-4d08-8cc5-1f7cdbdb9534/result",
  "error": null
}
```

В `pending`: `type`, `resultPath`, `error` равны `null`, `colors: []`. Даже уже полученный тип не выдаётся за полную готовность до проверки вырезки. В `failed`: безопасный `error` из списка ниже, тип и результат отсутствуют. Ошибка не создаёт готовую карточку. `GET /v1/items/{itemId}/operations/{operationId}` согласует конкретную попытку: `404 not_found` означает, что она ещё не принята и можно повторить тот же POST; `409 operation_superseded` означает, что она заменена и её нельзя автоматически активировать снова. Путь `resultPath` привязан к операции и возвращает PNG только для её текущего `ready`; иначе `409 not_ready` или `409 operation_superseded`. Старый URL `/v1/items/{itemId}/result` остаётся алиасом текущего результата, но новый клиент использует только путь с операцией: запоздавшее чтение не получит PNG другого снимка. Клиент сохраняет PNG до локального перехода в `ready`; готовая карточка читается без сети после перезапуска.

Ошибки имеют вид `{"error":"code"}`: `400 invalid_identity|invalid_image|invalid_request|invalid_attempt`, `401 unauthorized`, `404 not_found`, `409 identity_conflict|not_ready|stale_revision|operation_superseded`, `410 item_deleted|result_expired|result_delivered`, `413 image_too_large`, `415 unsupported_image|unsupported_content_type`. В ответах и логах нет содержимого фото и токенов. Ответы запрещают HTTP-кэширование.

## Подтверждение доставки и истечение

`POST /v1/items/{itemId}/operations/{operationId}/ack` требует токен владельца и корректные UUID, тело не нужно. Клиент отправляет его только после надёжной локальной записи PNG и готовой карточки. Текущая готовая операция атомарно очищает серверные изображения и признаки, получает отметку доставки и возвращает `204` без тела. Текущая активная `pending` или `failed` возвращает `409 not_ready`. Уже подтверждённая, истёкшая, удалённая, неизвестная или заменённая операция даёт идемпотентный `204` без изменения новой операции. Потерянное подтверждение можно повторять после перезапуска. Неверный UUID — `400 invalid_identity`; отсутствие доступа — `401 unauthorized`.

Срок — семь дней с приёма фото конкретной попытки. Ретрансляция той же операции не обновляет срок и не вызывает обработку. Каждый новый явный повтор или замена получает свой срок. Очистка выполняется до возобновления worker при запуске, каждую секунду работающего процесса, перед чтением/допуском загрузки и до/после внешних этапов. Незавершённые и ошибочные попытки также истекают; новые этапы после истечения не запускаются, поздние успехи и ошибки не возвращают очищенные данные.

После очистки `GET` состояния и повтор POST текущей операции возвращают идентичность и `status: failed`, `error: result_delivered` либо `result_expired`, `type: null`, `colors: []`, `resultPath: null`, состояния этапов `cleared`. Оба URL результата дают `410` с тем же безопасным кодом. Старые операции по-прежнему получают `409 operation_superseded`, удалённая вещь — `410 item_deleted`. Явная новая попытка разрешена после доставки/истечения и запрещена после удаления вещи. Для уже известного снимка проверяется сохранённый хеш нормализованных байтов: очистка исходника не разрешает незаметно заменить фото под прежним UUID.

Изображения, признаки и прежние ошибки удаляются атомарно; технические UUID, ревизии, сроки и записи идемпотентности с хешами остаются до удаления вещи. Это очистка данных приложения, без обещания физического стирания SQLite/WAL или копий у внешних провайдеров. При остановленном dev-стенде публичные тестовые фото могут физически оставаться до следующего запуска согласно [ADR-0002](../adr/0002-managed-dev-hosting.md); исключение не распространяется на личные фото. Уже сохранённая клиентская карточка не зависит от серверной копии.

## Удаление

`DELETE /v1/items/{itemId}` требует токен владельца, принимает UUID без тела запроса и возвращает `204` с пустым телом. Команду можно повторять после потери ответа и перезапуска: существующая, уже удалённая и ещё не загруженная вещь дают одинаковый `204`. Некорректный UUID — `400 invalid_identity`. Регистр UUID не имеет значения.

В одной транзакции backend записывает постоянную отметку удалённого `itemId`, удаляет текущий снимок, вырезку, признаки, состояние обработки и журнал приёма всех операций этой вещи. Отметка содержит только `itemId`, без фото, хешей снимков, операций и временных меток; она сохраняется без срока, чтобы запоздалые запросы не восстановили вещь. История `operationId` удалённой вещи больше не хранится; защита от восстановления привязана к её `itemId`.

После удаления все чтения этой вещи — текущее состояние, конкретная операция, её результат и старый алиас результата — возвращают `410 {"error":"item_deleted"}`. Оба маршрута загрузки отвергают корректные запросы с тем же `itemId` этим же ответом: старую принятую операцию, новый UUID операции и любую большую ревизию. Проверка выполняется после асинхронного чтения и нормализации фото, поэтому удаление, пришедшее во время загрузки, тоже побеждает. Неизвестный неудалённый ID по-прежнему даёт `404` при чтении.

Клиент скрывает вещь и сохраняет команду удаления без сети. Пока команда не дошла, backend может закончить уже принятую работу; последующее удаление очищает и готовый результат. После приёма удаления ещё не начатые этапы не обращаются к провайдерам. Уже отправленный внешний запрос может закончиться, но ни успех, ни ошибка не создают новую запись или доступный результат. Это удаление записей приложения; оно не обещает физическое стирание остаточных байтов SQLite/WAL или удаление данных у внешнего провайдера.

## Этапы и ошибки обработки

`processing.attributes` и `processing.cutout` имеют значения `pending`, `in_flight`, `done`, `failed`, `unknown`, `cleared`. Последнее означает, что временные данные этапа уже очищены. Сначала проверяются фото, тип и цвета, затем удаляется фон. Перед внешним вызовом сохраняется `in_flight`, после успешной проверки ответа — `done` вместе с результатом. Перезапуск продолжает только `pending`. Оставшийся `in_flight` превращается в `unknown`, а карточка — в `failed` с `processing_unknown`. Повторный POST не сбрасывает это состояние и не расходует квоту ещё раз. Приложение сохраняет исходник и показывает необходимость разбора результата; автоматического повторного AI-вызова нет.

Таймеры и обновления worker привязаны к операции. Поздний успех или ошибка старого снимка не меняет текущую попытку; поздние признаки старой операции не запускают её следующий этап. При обновлении старой базы добавляются ревизия 0 и журнал приёма. Серверные данные без сохранённого срока загрузки консервативно истекают до старта worker: неизвестный возраст не даёт нового семидневного срока. Идентичность и хеши сохраняются для явного повтора; локальные готовые карточки не затрагиваются.

Коды ошибок обработки:

| Код | Значение |
| --- | --- |
| `provider_not_configured` | Отсутствуют ключи или настройки обработчика некорректны |
| `provider_preflight_required` | Не подтверждены аккаунты, бесплатные квоты и opt-out Photoroom |
| `provider_unauthorized` | Провайдер отказал в доступе |
| `provider_quota_exceeded` | Провайдер сообщил об исчерпании квоты/необходимости оплаты |
| `provider_rejected` | Провайдер явно отклонил запрос |
| `invalid_provider_response` | Ответ неполный, некорректный, слишком большой или не содержит пригодной вырезки |
| `photo_on_person` | Вещь сфотографирована на человеке |
| `photo_multiple_items` | Обнаружены несколько отдельных вещей |
| `photo_no_item` | Вещь не обнаружена |
| `photo_unclear` | Фото неоднозначно для распознавания |
| `inappropriate_photo` | Провайдер не разрешил обработку фото |
| `image_too_large` | Нормализованный PNG превышает предел внешней передачи 5 MiB |
| `processing_unknown` | Запрос мог выполниться; автоматический повтор запрещён |
| `provider_configuration_changed` | Сменился обработчик принятой операции; подмена результата запрещена |
| `processing_failed` | Управляемая ошибка demo |
| `result_expired` | Временная копия истекла; возможен явный повтор из клиентского исходника |
| `result_delivered` | Клиент подтвердил сохранение; серверная копия уже очищена |

`mode` сохраняется с операцией и результатом. Backend также различает реальный обработчик, управляемый HTTP-транспорт и синтетический demo внутренним идентификатором, чтобы перезапуск не подменял один другим. Непросроченные задания с сохранённым сроком продолжаются после перезапуска; истёкшие не запускают провайдера.

## Границы среза

SQLite сохраняет очередь, снимок, готовые этапы и результат между перезапусками одного backend-процесса. [Конфигурация и допуск провайдеров](../../backend/README.md), [протоколы и источники](provider-integration.md). Ручные правки типа и цветов хранятся только на клиенте и не меняют контракт API; обработка не перезаписывает их. Явные повторы и замена фото используют ту же вещь; прежняя хорошая вырезка хранится на клиенте до успешного получения новой. Backend хранит только текущий снимок/результат и журнал идентичности принятых операций. После удаления остаётся только отметка ID. Срок временного хранения и подтверждение доставки реализованы; deployment относится к следующей задаче. Используйте синтетические фото локально. Настоящая проба на публичных фото — #10; личные фото пока не разрешены.

## Идентичность dev-выкладки и совместимость хранилища

Публичный `GET /health` дополнительно сообщает `revision` (встроенный полный SHA, либо `development` для локального запуска без release-файла), `dataVersion: 1` и необязательный `deploymentId` из `SAINT_LOOK_DEPLOYMENT_ID`. Workflow задаёт новый UUID на каждую выкладку: это маркер приложения, не native Fly Machine/release ID. SHA не берётся из mutable environment variable; сочетание SHA и маркера позволяет отличить две выкладки одного SHA. Обычный перезапуск сохраняет маркер. Успешный healthcheck не заменяет проверку авторизованной цепочки до PNG.

Контролируемый контейнерный профиль использует настоящий HTTP-адаптер с loopback-провайдерами и возвращает `mode: demo`, даже если окружение содержит live-ключи. Их квота не расходуется. Управление fixture не публикуется через API backend.

SQLite `user_version` проверяется до инициализации схемы и worker. Этот release принимает прежнюю немаркированную базу (0 → 1) и версию 1; более новая или иная неподдерживаемая версия останавливает startup. Откат приложения не является откатом данных; повторная доступность подтверждается ожидаемыми SHA/deployment ID и API smoke.
