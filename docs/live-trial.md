# Первая проба настоящих API: #10

## Текущий режим — sandbox Photoroom, 26 октября 2026

Владелец подтвердил настоящую обработку футболки, худи и брюк на iPhone,
сохранение карточек после офлайн-перезапуска и ручную проверку PhotosPicker.
После этой приёмки он явно выбрал **sandbox Photoroom до нового прямого запроса
переключиться на production**. При текущем режиме вырезки содержат watermark;
Jev по-прежнему использует свой обычный API и кредиты.

Live workflow передаёт `PHOTOROOM_SANDBOX_API_KEY` в серверную переменную
`PHOTOROOM_API_KEY`. Production-секрет `PHOTOROOM_API_KEY` хранится отдельно
и этим workflow не читается. Автоматического fallback на production нет.
`mode=live` в приложении означает настоящие внешние API, а не платную квоту
Photoroom. Для смены ключа новая IPA не нужна; прежние результаты не меняются.

Не переключайте ключ и не выполняйте расходующие production-пробы без нового
явного запроса владельца. Флаг `AI_TRIAL_PREFLIGHT_VERIFIED` сам по себе такого
разрешения не даёт. До слияния изменения workflow этот флаг выключен, чтобы
прежняя версия workflow не вернула production-ключ. После слияния и проверки
аккаунтов его можно включить для sandbox-выкладок.

Описанный ниже первоначальный план clean production-пробы — исторический
контекст приёмки, а не разрешение вновь расходовать production-квоту.

Этот путь подготовлен для 2–3 публичных фото одной вещи вне человека. Реальная проба ещё не выполнена: аккаунты, ключи, доступность Jev, остаток кредитов и квоты Photoroom и API opt-out требуют фактической проверки. Успешный controlled CI не закрывает #10. Ручная проверка PhotosPicker на Mac отложена в #13; автоматический импорт ресурсов ниже её не подменяет.

## До допуска

Используйте [проверку аккаунтов](research/provider-account-preflight.md): правильные Space/организацию, регион клиента, остатки кредитов/квот и согласованный бюджет, применимые API-настройки использования фото. Наличие Fly в AMS само по себе не подтверждает доступность провайдеров для пользователя. Выбраны Photoroom Basic (ориентир $20/месяц за 1000 вырезок) и Jev; начальную пробу можно провести на доступных 10 бесплатных production-вызовах Photoroom. Минимальное пополнение Jev проверяется в аккаунте; автоматическое пополнение не включаем.

По умолчанию выбраны первые два фото из [manifest](../client-ios/SaintLook/TrialPhotos/manifest.json); третий снимок — отдельный выбор. Их источники, лицензии и неизменённые SHA-256 записаны в manifest и [исследовании](research/live-trial-images.md). Перед запуском подтвердите допустимость этих публичных снимков для выбранных аккаунтов. При распространении видео и результатов сохраняйте ATTRIBUTION.md и соблюдайте соответствующие CC BY-SA условия.

В GitHub Repository → Settings → Secrets and variables → Actions добавьте **secrets** `TYPESAFE_API_KEY` и `PHOTOROOM_API_KEY`. С телефона можно пользоваться этой страницей GitHub; ключи не пересылаются в чат. CLI-альтернатива — интерактивный `gh secret set TYPESAFE_API_KEY` / `gh secret set PHOTOROOM_API_KEY`, без значения в аргументах. Существующие `FLY_API_TOKEN` и `SAINT_LOOK_DEV_OWNER_TOKEN` остаются прежними. Ключи AI не передаются iOS или XCTest.

После фактической проверки условий и остатка квот установите repository **variable** `AI_TRIAL_PREFLIGHT_VERIFIED=true`. Это ручное подтверждение текущей проверки аккаунтов, не автоматическая проверка тарифа, остатка или потолок расходов. Не устанавливайте её лишь потому, что ключи созданы. Обычный Fly/Actions budget guard остаётся обязательным. Перед каждым новым расходующим запуском проверяйте остаток заново.

Запишите до пробы: время, регион и применимые условия Jev, организацию и модель `jev-1.14.0`, кредиты/лимиты, остаток production Remove Background вызовов Photoroom, подтверждение API opt-out и выбранные файлы. Не публикуйте ключи, идентификаторы аккаунтов или лишние персональные данные.

## Выкладка live и расходующая проба

1. Влейте подготовленную версию и дождитесь полного успешного **main push CI** на её точном SHA. Manifest нового релиза разрешает `live`; старые controlled-only и Gemini-релизы для live отвергаются по `providerConfig`. Обычная ручная выкладка остаётся controlled независимо от наличия настоящих ключей.
2. Завершите или явно удалите прежнюю ожидающую обработку перед сменой профиля. При наличии pending-операций другого `provider_id` (включая прежнюю модель/справочник) новый runtime отказывается запускаться до worker, сохраняя операции; верните прежний профиль для их завершения/удаления. Не редактируйте SQLite ради обхода проверки. Время хранения продолжает действовать.
3. В Actions выберите **Deploy live profile and optionally run approved photo trial**, branch **main**, полный SHA, `run_trial=false` для первой проверки запуска. Ключи передаются Fly через stdin команды `secrets import --stage`; версия собирается локально runner и использует тот же volume. Установлен явный `SAINT_LOOK_DEPLOYMENT_PROFILE=live` и подтверждённый preflight. Новый launcher запускает обычный production backend без fixture и отклоняет тестовые overrides.
4. Live deploy выполняет только `/health`: проверяет SHA, свежий маркер выкладки, формат данных 1 и `mode=live`. Он **не создаёт новых upload-запросов**. Ранее принятые pending-операции того же live-провайдера могут возобновиться при запуске и расходовать квоту; учтите их перед выкладкой. Неизвестный исход уже начатого вызова не повторяется автоматически.
5. После проверки аккаунтов и readiness запустите workflow с `run_trial=true`, `photo_count=2` (или явно `3`). Он снова выкладывает выбранный проверенный SHA и берёт из этого же коммита клиент, `LiveTrialTests`, скрипт Simulator, фото и их manifest/ATTRIBUTION. Клиент и backend используют одну версию с успешным main push CI; текущий main предоставляет workflow и release guards. Затем запускается только `LiveTrialTests`. Перед UI-действиями скрипт проверяет manifest, число фото и SHA-256 файлов. Каждый выбранный снимок импортируется **один раз** через тот же `WardrobeStore.addPhoto` и нормализацию, что PhotosPicker; новый запрос к Jev и Photoroom не создаётся отдельно API-smoke. Не нажимайте Re-run для повторения неизвестного исхода без проверки фактической квоты.
6. Тест требует настоящего `mode=live`, готовой вырезки, непустого типа и цветов, затем перезапускает приложение без сети и сравнивает сохранённую карточку. Название и цвета заранее не фиксируются. Неудачный результат не вызывает автоматического retry/замены фото; XCTest-retry не включён. Готовые карточки оставляются в Simulator для просмотра, затем соединение возвращается для доставки ack. Ручная демонстрация на интерактивном Mac и оценка качества записываются отдельно.

Скрытая кнопка импорта доступна только в Debug с `SAINT_LOOK_UI_TESTING=1` и `SAINT_LOOK_LIVE_TRIAL=1`; обычный UI продолжает использовать PhotosPicker. Публичные ресурсы входят в bundle, но Release не содержит код их тестового импорта. Обычный CI пропускает LiveTrialTests до сетевых действий; combined replacement → delete → late result проверяется управляемыми ответами на HTTP- и UI-границах.

Обе workflow используют одну concurrency group, поэтому обычная выкладка не прервёт live-пробу. Автоматического отката после ошибки нет: сначала проверьте состояние и исход уже начатых вызовов. Истечение/отключение допуска не останавливает уже работающий live-backend.

## Результат и завершение

Workflow записывает общий проверенный SHA клиента/backend, маркер и выбранное число снимков; MP4, manifest, ATTRIBUTION и инструкция сохраняются 7 дней. `.xcresult` и XCTest environment не публикуются. Число выбранных фото — не доказательство фактического списания: в отчёт #10 отдельно внесите остаток/историю провайдеров **до и после**, результаты каждого фото, наблюдаемые ошибки границ/цвета/типа, ручную проверку и ограничения. Не называйте 2–3 удачных снимка доказательством общего качества или числового SLA.

После согласованной разовой пробы верните controlled-профиль обычным **Deploy checked Fly dev release** на совместимом проверенном SHA. Он явно сбрасывает профиль и preflight; наличие настоящих секретов не включает AI. Сначала завершите/удалите pending live-операции через обычный клиент. Отмените `AI_TRIAL_PREFLIGHT_VERIFIED` до следующей проверки аккаунтов. Возврат кода сохраняет текущую базу, а не восстанавливает прежние данные.

#10 остаётся открытой до фактической цепочки через настоящие API, проверки карточек после перезапуска и записи использованной квоты. Отсутствующие аккаунты или ручной шаг нельзя заменять успехом локального CI.
