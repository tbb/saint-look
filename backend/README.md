# Backend добавления вещи

Node.js 24 LTS (минимум 24.13), встроенные HTTP и SQLite, одна runtime-зависимость `sharp` для декодирования и удаления метаданных. SQLite хранит нормализованный снимок, этапы обработки и результат в приватном каталоге. Один процесс обслуживает API и очередь; одновременный запуск нескольких экземпляров на одном файле базы не поддерживается.

## Локальный demo

```bash
npm --prefix backend ci --ignore-scripts
export SAINT_LOOK_OWNER_TOKEN="$(node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))')"
export SAINT_LOOK_PROVIDER=demo
node backend/src/server.mjs
```

Тот же токен задайте в настройках приложения. Не сохраняйте его в Git, URL или логах. Сервер пишет только локальный адрес и режим, не запросы. Рабочие данные по умолчанию `.data/wardrobe.sqlite`, исключены из Git; права новых файлов ограничены `umask 077`. `SAINT_LOOK_DATA_DIR` меняет каталог; `PORT` — порт (8787), `HOST` — интерфейс (127.0.0.1).

Demo возвращает синтетическую футболку независимо от фото. `SAINT_LOOK_DEMO_DELAY_MS` задаёт начальную задержку (1500 мс по умолчанию), `SAINT_LOOK_DEMO_OUTCOME=fail` — управляемый отказ. Здесь нет ключей провайдера или внешних AI-вызовов.

## Реальные провайдеры: допуск перед запуском

`SAINT_LOOK_PROVIDER=live` выбирает Gemini `gemini-3.1-flash-lite` для проверки фото, типа и цветов, затем Photoroom Remove Background для PNG-вырезки. Используется только `/v1/segment`, без генерации изображения и с `despill=false`, чтобы не менять цвета. Тип и цвета проходят проверку, PNG должен быть декодируемым, непустым и иметь прозрачность. Карточка становится готовой только после обоих этапов.

Перед настоящим запуском оператор проверяет доступность обоих аккаунтов, остаток бесплатных квот, отсутствие разрешённого платного продолжения и opt-out обучения Photoroom. Только после этого задаются `GEMINI_API_KEY`, `PHOTOROOM_API_KEY` и `SAINT_LOOK_PROVIDER_PREFLIGHT_CONFIRMED=true` на backend. **Флаг означает ручное подтверждение, а не автоматическую проверку аккаунтов.** Ключи не читаются клиентом. Backend не меняет тарифы, не пополняет квоты и не переключается в demo при ошибке. При отсутствии ключа/допуска принятая операция завершается понятной ошибкой до внешнего запроса.

Настоящие аккаунты и качество обработки пока не проверены. Проба на 2–3 публичных фотографиях относится к #10; наличие адаптеров не заменяет её. Личные фотографии этим запуском не разрешены. [Проверенные протоколы и условия](../docs/api/provider-integration.md).

Нормализованный PNG для внешней передачи ограничен 5 MiB; компактный JPEG может превысить этот предел после декодирования и получить `image_too_large` до обращения к провайдерам. Ответ Gemini ограничен 64 KiB, ответ Photoroom и сохранённая PNG-вырезка — 10 MiB и 16 MP. `SAINT_LOOK_PROVIDER_TIMEOUT_MS` — таймаут одного внешнего запроса (60000 мс по умолчанию, 50–120000).

## Очередь и перезапуск

Намерение внешнего вызова записывается до отправки, успешный этап — до следующего этапа. После перезапуска очередь продолжает только ещё не начатые этапы; готовые этапы повторно не вызываются. Таймаут, разрыв соединения, ответ 5xx или авария во время внешнего запроса оставляют `processing_unknown`. Такой исход требует разбора и **не повторяется автоматически**, даже при повторном POST от клиента. Успешно полученные признаки сохраняются отдельно от ещё не готовой вырезки. Режим операции записан при приёме: смена обработчика не может незаметно выдать синтетический результат для прежней операции.

`SAINT_LOOK_STAGE_DELAY_MS` задаёт паузу перед этапами (0 по умолчанию) и помогает управляемо проверять остановку между этапами. Для demo начальная задержка задаётся отдельной переменной выше. Перед возобновлением очереди очищаются просроченные данные. Готовые локальные карточки остаются на клиенте независимо от состояния backend; удалённый dev-стенд на Fly.io работает в режиме управляемых HTTP-ответов провайдеров. [Проверенные выкладки и сохранность данных](../docs/deployment.md#проверка-25-октября-2026).

## Новые попытки обработки

Явный повтор или замена фото принимаются в той же вещи через `POST /v1/items/{itemId}/attempts`. Новая операция получает большую ревизию; повторная доставка не создаёт второй внешний вызов. Сохранённые записи приёма не позволяют запоздавшему старому запросу вернуть прежний снимок. Результат доступен по URL, привязанному к операции. Поздние ответы предыдущей обработки не меняют новую карточку; уже запущенный внешний вызов может закончиться, но его результат отбрасывается. Полный контракт — [здесь](../docs/api/local-ingestion.md).

База без ревизий получает `revision=0` и журнал принятых операций. При переходе на #8 старые серверные копии без срока загрузки считаются просроченными и очищаются: их возраст неизвестен, выдавать им дополнительные семь дней нельзя. UUID и журнал остаются для безопасного явного повтора из клиентского исходника. Уже сохранённые клиентские карточки не затрагиваются. Старый backend не понимает новые ревизии, поэтому запуск прежнего бинарника поверх обновлённых данных не является безопасным откатом данных.

## Удаление вещи

Авторизованный `DELETE /v1/items/{itemId}` возвращает `204`, в том числе при повторе и для ещё не загруженного UUID. SQLite одной транзакцией удаляет снимок, результат, признаки, очередь и журнал операций вещи, сохраняя только постоянную отметку её `itemId`. Любая последующая загрузка или чтение этого ID получает `410 item_deleted`, включая запрос, начатый до удаления и допущенный после нормализации фото. Отметка переживает перезапуск; новый UUID операции или большая ревизия не восстанавливают вещь.

Ещё не начатые внешние этапы не выполняются. Ответ уже отправленного запроса может прийти, но worker не публикует его и не создаёт вещь заново. Если обработка закончилась до доставки офлайн-команды, удаляется готовый результат. Очищаются записи приложения, без обещания физического стирания SQLite/WAL или данных у провайдера. Постоянные отметки содержат только UUID и не истекают вместе с временными результатами.

## Проверки

```bash
npm --prefix backend test
npm --prefix backend run check
```

Тесты запускают настоящий сервер и SQLite, общаются через HTTP. Внешние ответы контролируются локальным HTTP-сервером с настоящими форматами Gemini и Photoroom. `SAINT_LOOK_TEST_PROVIDER_ORIGIN` разрешён только при `NODE_ENV=test`, только HTTP на `127.0.0.1` или `::1`; обе внешние точки заменяются вместе. Такой транспорт выдаёт `mode: demo`, чтобы не заявлять настоящий AI. В тестовом окружении live без локального адреса блокируется. Фото синтетические; реальные ключи и аккаунты не используются. [Контракт](../docs/api/local-ingestion.md), [iOS-клиент](../client-ios/README.md).


Для Simulator CI есть отдельный тестовый HTTP-сервер `NODE_ENV=test node backend/test/providers/ui-server.mjs` (loopback8789). Он отвечает в форматах Gemini/Photoroom, по умолчанию выдаёт синтетическую синюю футболку, а защищённый тестовым токеном `/__control` задаёт одноразовый отказ проверки фото, квоты или красную тестовую вырезку. Эти команды находятся только в тестовом сервере; рабочий backend не содержит маршрутов управления провайдерами. UI-тесты используют настоящие API, очередь и SQLite с этими управляемыми внешними ответами.


## Подтверждение доставки и срок хранения

Клиент отправляет `POST /v1/items/{itemId}/operations/{operationId}/ack` только после записи PNG и готовой карточки на своё устройство. Ответ `204` означает, что серверная копия этой попытки очищена или уже отсутствует. Повтор команды безопасен; старое подтверждение не удаляет новую попытку. Подтверждение текущей незавершённой/ошибочной обработки даёт `409 not_ready`.

Временные снимок, признаки и вырезка живут не более семи дней с приёма загрузки попытки. Повторная доставка той же операции не продлевает срок; явная новая попытка из локального исходника получает новый срок. Очистка выполняется после подтверждения, при запуске до очереди, каждую секунду работающего процесса, а также на границах запросов и внешних этапов. Истёкший результат никогда не выдаётся как актуальный; поздний внешний ответ не публикует его снова. Очищаются изображения и признаки, остаются только технические идентификаторы, ревизия, срок, отметка состояния и журнал с хешами снимков для идемпотентности.

Состояние очищенной текущей попытки возвращает `failed` с `result_delivered` или `result_expired`; URL PNG — `410` с тем же кодом. Уже готовая локальная карточка продолжает работать офлайн. Незабранный результат требует явного повтора из локального исходника, без автоматического нового AI-вызова.

Согласно [ADR-0002](../docs/adr/0002-managed-dev-hosting.md), при остановленном dev-backend физическая очистка публичных тестовых фото может ждать следующего запуска. Это исключение не разрешает личные фото и не обещает такой же срок у AI-провайдера. Очистка данных приложения не является гарантией физического стирания остаточных байтов SQLite/WAL. Возврат старого бинарника не восстанавливает очищенные данные и не является безопасным откатом этой схемы.

## Управляемое время тестов

API и UI используют настоящий backend и SQLite. Только для `NODE_ENV=test` вместе с корректным loopback `SAINT_LOOK_TEST_PROVIDER_ORIGIN` и обработчиком `live-test` можно задать `SAINT_LOOK_TEST_CLOCK_FILE`: JSON-файл `{"offsetMs":0}`. Часы равны текущему времени плюс целое смещение от 0 до 31536000000 мс (365 дней); TTL остаётся фиксированным, семь дней. Тест меняет файл атомарно, не редактируя базу или состояние очереди. Неизолированная конфигурация или некорректное смещение блокируют запуск. При отсутствии переменной используются обычные часы. Рабочий API не имеет маршрута управления временем.

## Контейнер dev-стенда

`backend/Dockerfile` собирается из корня репозитория и запускает `src/start-release.mjs`, который по умолчанию выбирает `src/start-controlled.mjs`. Этот профиль предназначен для dev-стенда с публичными тестовыми фото: он поднимает HTTP-ответы Gemini/Photoroom только на случайном loopback-порту, а настоящий адаптер backend обращается к ним. Режим API — `demo`. Значения `SAINT_LOOK_PROVIDER`, внешнего test-origin, AI-ключей и test-clock из окружения не могут переключить этот launcher на реальные API. Для настоящей пробы #10 подготовлен отдельный явный live-путь этого образа; обычная выкладка его не включает.

Launcher требует файл `backend/REVISION` с полным SHA исходников, включённый в образ при сборке. `/health` возвращает `revision`, `dataVersion: 1` и необязательный `deploymentId` из `SAINT_LOOK_DEPLOYMENT_ID`. Workflow задаёт новый UUID для каждой выкладки: это наш маркер попытки deploy, не native Fly Machine/release ID. Он позволяет отличить две выкладки одного SHA; обычный перезапуск без новой выкладки сохраняет маркер. Переменные платформы не являются источником версии образа. Обычный локальный `src/server.mjs` без файла сообщает `revision: development`. При отказе любого дочернего процесса launcher завершает другой и выходит с ошибкой; SIGTERM останавливает оба процесса, затем через 8 секунд принудительно завершает оставшиеся.

Образ закреплён на Node **24.21.0 bookworm-slim** и digest manifest. Версия проверена по [Node release](https://nodejs.org/en/blog/release/v24.21.0), вариант — по [официальному Docker Node](https://github.com/nodejs/docker-node); digest получен из Docker Registry 2026-10-24. `npm ci --omit=dev --ignore-scripts` использует lockfile. `.dockerignore` допускает только runtime, manifest, встроенный SHA и один контролируемый HTTP-сервер; локальные фото, токены и `.env` не попадают в build context.

Каталог данных — `/data`, интерфейс — `0.0.0.0`, порт — `PORT=8080`. Нужны одна Fly Machine и существующий volume `saint_look_data` на 3 GB в `ams`, без scheduled snapshots. Образ работает с UID 0 из-за прав mounted volume. `fly.toml` задаёт Dockerfile, `/health`, HTTPS, shared CPU / 1024 MB RAM, mount `/data`, отключённые autostop/autostart и scheduled snapshots, 15 секунд на остановку и три перезапуска при ошибке. Значение `initial_size` ограничивает конфигурацию первоначального диска; оно не является проверкой существующего volume. Число Machines и фактический volume проверяет путь выкладки; сам config не ограничивает общий счёт. Имя существующего приложения передаётся явно через `--app`. Перед запуском нужна проверка ресурсов и бюджета по [инструкции выкладки](../docs/deployment.md). Поля сверены с [официальной Fly configuration reference](https://docs.fly.io/reference/configuration).

Локальная проверка настоящего контейнера (нужен Docker; SHA должен соответствовать собранному checkout):

```bash
git rev-parse HEAD > backend/REVISION
docker build -f backend/Dockerfile -t saint-look-ci .
node backend/test/container-smoke.mjs saint-look-ci "$(git rev-parse HEAD)"
rm backend/REVISION
```

Smoke создаёт отдельный volume и контейнер, проверяет авторизацию, обработку через HTTP-провайдеры, PNG и SHA; затем запускает новый контейнер с тем же volume и сверяет сохранённый результат. После проверки ACK и удаления контейнеры и volume очищаются. Это локальная проверка Docker, не доказательство реальной выкладки или rollback на Fly.io.

## Совместимость данных и возврат кода

`backend/release.json` фиксирует `format`, `profile`, `dataVersion` и поддерживаемый диапазон версий данных. SQLite `user_version` — постоянный маркер формата: существующая база с 0 получает 1, поскольку структура приложения не меняется. Неподдерживаемая версия отвергается **до миграций, переключения WAL и запуска worker**. Будущее изменение формата должно обновлять manifest и маркер; нельзя понижать маркер ради запуска старого кода.

Возврат приложения выбирает прежний проверенный SHA с совместимым manifest и использует текущий volume. Он не возвращает удалённые фото, не отменяет ACK/TTL и не откатывает содержимое SQLite. Версии до этого контракта не считаются безопасной целью workflow rollback. Успех реального возврата требует отдельной проверки на Fly.io; без неё доступны только локальные результаты процесса/контейнера.

Новый релиз также объявляет явную capability `live`; запуск и ограничения описаны в [инструкции пробы](../docs/live-trial.md). По умолчанию `start-release.mjs` запускает controlled. Для live нужны явный профиль, подтверждённые условия аккаунтов и ключи; тестовые overrides запрещены. При pending-операциях другого провайдера deployed runtime отказывается запускать worker, чтобы не менять их профиль.
