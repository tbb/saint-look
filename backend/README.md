# Backend добавления вещи

Node.js 24 LTS (минимум 24.13), встроенные HTTP и SQLite, одна runtime-зависимость `sharp` для декодирования и удаления метаданных. SQLite хранит нормализованный снимок, этапы обработки и результат в приватном каталоге. Один процесс обслуживает API и очередь; одновременный запуск нескольких экземпляров на одном файле базы не поддерживается.

## Локальный demo

```bash
npm --prefix backend ci --ignore-scripts
export SAINT_LOOK_OWNER_TOKEN="$(node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))')"
export SAINT_LOOK_PROVIDER=demo
node backend/src/server.mjs
```

Тот же токен задайте в настройках приложения. Не сохраняйте его в Git, URL или логах. Сервер пишет только локальный адрес и режим, не запросы. Рабочие данные по умолчанию `.data/wardrobe.sqlite`, исключены из Git; права новых файлов ограничены `umask 077`. `SAINT_LOOK_DATA_DIR` меняет каталог; `PORT` — порт (8787), `HOST` — интерфейс (127.0.0.1).

Demo возвращает синтетическую футболку независимо от фото. `SAINT_LOOK_DEMO_DELAY_MS` задаёт начальную задержку (1500 мс по умолчанию), `SAINT_LOOK_DEMO_OUTCOME=fail` — управляемый отказ. Здесь нет ключей провайдера или внешних AI-вызовов.

## Реальные провайдеры: допуск перед запуском

`SAINT_LOOK_PROVIDER=live` выбирает Gemini `gemini-3.1-flash-lite` для проверки фото, типа и цветов, затем Photoroom Remove Background для PNG-вырезки. Используется только `/v1/segment`, без генерации изображения и с `despill=false`, чтобы не менять цвета. Тип и цвета проходят проверку, PNG должен быть декодируемым, непустым и иметь прозрачность. Карточка становится готовой только после обоих этапов.

Перед настоящим запуском оператор проверяет доступность обоих аккаунтов, остаток бесплатных квот, отсутствие разрешённого платного продолжения и opt-out обучения Photoroom. Только после этого задаются `GEMINI_API_KEY`, `PHOTOROOM_API_KEY` и `SAINT_LOOK_PROVIDER_PREFLIGHT_CONFIRMED=true` на backend. **Флаг означает ручное подтверждение, а не автоматическую проверку аккаунтов.** Ключи не читаются клиентом. Backend не меняет тарифы, не пополняет квоты и не переключается в demo при ошибке. При отсутствии ключа/допуска принятая операция завершается понятной ошибкой до внешнего запроса.

Настоящие аккаунты и качество обработки пока не проверены. Проба на 2–3 публичных фотографиях относится к #10; наличие адаптеров не заменяет её. Личные фотографии этим запуском не разрешены. [Проверенные протоколы и условия](../docs/api/provider-integration.md).

Нормализованный PNG для внешней передачи ограничен 5 MiB; компактный JPEG может превысить этот предел после декодирования и получить `image_too_large` до обращения к провайдерам. Ответ Gemini ограничен 64 KiB, ответ Photoroom и сохранённая PNG-вырезка — 10 MiB и 16 MP. `SAINT_LOOK_PROVIDER_TIMEOUT_MS` — таймаут одного внешнего запроса (60000 мс по умолчанию, 50–120000).

## Очередь и перезапуск

Намерение внешнего вызова записывается до отправки, успешный этап — до следующего этапа. После перезапуска очередь продолжает только ещё не начатые этапы; готовые этапы повторно не вызываются. Таймаут, разрыв соединения, ответ 5xx или авария во время внешнего запроса оставляют `processing_unknown`. Такой исход требует разбора и **не повторяется автоматически**, даже при повторном POST от клиента. Успешно полученные признаки сохраняются отдельно от ещё не готовой вырезки. Режим операции записан при приёме: смена обработчика не может незаметно выдать синтетический результат для прежней операции.

`SAINT_LOOK_STAGE_DELAY_MS` задаёт паузу перед этапами (0 по умолчанию) и помогает управляемо проверять остановку между этапами. Для demo начальная задержка задаётся отдельной переменной выше. Каталог #2 читается после добавления полей журнала; готовые карточки сохраняются. Срок хранения неудалённых вещей относится к следующей задаче, поэтому стенд ещё нельзя считать готовым к личным фото или внешнему deployment.

## Новые попытки обработки

Явный повтор или замена фото принимаются в той же вещи через `POST /v1/items/{itemId}/attempts`. Новая операция получает большую ревизию; повторная доставка не создаёт второй внешний вызов. Сохранённые записи приёма не позволяют запоздавшему старому запросу вернуть прежний снимок. Результат доступен по URL, привязанному к операции. Поздние ответы предыдущей обработки не меняют новую карточку; уже запущенный внешний вызов может закончиться, но его результат отбрасывается. Полный контракт — [здесь](../docs/api/local-ingestion.md).

Существующая база обновляется добавлением `revision=0` и журнала принятых операций. Исходники и результаты текущих готовых вещей сохраняются. Старый backend не понимает новые ревизии, поэтому запуск прежнего бинарника поверх обновлённых данных не является безопасным откатом данных.

## Удаление вещи

Авторизованный `DELETE /v1/items/{itemId}` возвращает `204`, в том числе при повторе и для ещё не загруженного UUID. SQLite одной транзакцией удаляет снимок, результат, признаки, очередь и журнал операций вещи, сохраняя только постоянную отметку её `itemId`. Любая последующая загрузка или чтение этого ID получает `410 item_deleted`, включая запрос, начатый до удаления и допущенный после нормализации фото. Отметка переживает перезапуск; новый UUID операции или большая ревизия не восстанавливают вещь.

Ещё не начатые внешние этапы не выполняются. Ответ уже отправленного запроса может прийти, но worker не публикует его и не создаёт вещь заново. Если обработка закончилась до доставки офлайн-команды, удаляется готовый результат. Очищаются записи приложения, без обещания физического стирания SQLite/WAL или данных у провайдера. Постоянные отметки содержат только UUID; автоматический срок хранения остальных вещей будет реализован отдельно в #8.

## Проверки

```bash
npm --prefix backend test
npm --prefix backend run check
```

Тесты запускают настоящий сервер и SQLite, общаются через HTTP. Внешние ответы контролируются локальным HTTP-сервером с настоящими форматами Gemini и Photoroom. `SAINT_LOOK_TEST_PROVIDER_ORIGIN` разрешён только при `NODE_ENV=test`, только HTTP на `127.0.0.1` или `::1`; обе внешние точки заменяются вместе. Такой транспорт выдаёт `mode: demo`, чтобы не заявлять настоящий AI. В тестовом окружении live без локального адреса блокируется. Фото синтетические; реальные ключи и аккаунты не используются. [Контракт](../docs/api/local-ingestion.md), [iOS-клиент](../client-ios/README.md).


Для Simulator CI есть отдельный тестовый HTTP-сервер `NODE_ENV=test node backend/test/providers/ui-server.mjs` (loopback8789). Он отвечает в форматах Gemini/Photoroom, по умолчанию выдаёт синтетическую синюю футболку, а защищённый тестовым токеном `/__control` задаёт одноразовый отказ проверки фото, квоты или красную тестовую вырезку. Эти команды находятся только в тестовом сервере; рабочий backend не содержит маршрутов управления провайдерами. UI-тесты используют настоящие API, очередь и SQLite с этими управляемыми внешними ответами.
