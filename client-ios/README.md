# iOS: добавление, редактирование и удаление вещей

SwiftUI-приложение для iOS 17+. Откройте `SaintLook.xcodeproj` в Xcode и выберите общую схему `SaintLook` и iPhone Simulator. Внешних Swift-пакетов нет. Для запуска на устройстве потребуется выбрать свой signing team; HTTP разрешён только для loopback, для удалённого backend нужен HTTPS.

Запустите локальный backend из `../backend` и укажите в настройках приложения его адрес и токен владельца. Simulator использует `http://127.0.0.1:8787` на Mac. Токен сохраняется в Keychain, фотографии и каталог — в Application Support. Ключи AI-провайдеров приложению не нужны.

«Добавить фото» открывает системный PhotosPicker без запроса доступа ко всей медиатеке. Исходник и pending-карточка сохраняются перед отправкой. Для backend приложение создаёт PNG без метаданных, с длинной стороной до 2048 px; исходник остаётся на устройстве. Лимиты: исходник до 20 MiB, отправляемая копия до 5 MiB. После получения результата вырезка, тип и цвета сохраняются локально и доступны после перезапуска без backend. При ошибке соединения карточка остаётся ожидающей. Пока приложение открыто, оно автоматически повторяет согласование с backend с паузой до 10 секунд; в фоне постоянная работа не требуется. Повтор использует прежние идентификаторы вещи, операции и снимка. Подробнее: [офлайн-восстановление](../docs/offline-ingestion.md).

Клиент различает режимы backend: `demo` явно обозначен в интерфейсе и на готовой карточке, `live` получает обычную отметку готовности. Режим результата сохраняется вместе с карточкой. Управляемые внешние ответы в тестах обозначены как demo; это не доказательство подключения настоящих аккаунтов. В Debug также есть кнопка «Добавить тестовое фото»: она создаёт изображение и вызывает тот же путь сохранения и отправки, что PhotosPicker. В Release кнопки и переменных окружения для UI-тестов нет.

## Ручные правки

Кнопка «Изменить тип и цвета» доступна у ожидающей, готовой и ошибочной карточки. Тип вводится текстом, основные цвета — через запятую. Изменения необязательны: добавление фотографии по-прежнему обходится без анкеты. Отмена закрывает форму без сохранения; при ошибке записи форма остаётся открытой.

Каждое изменённое поле хранится в локальном каталоге отдельно от автоматического значения. Правки сохраняются атомарно, работают без сети и переживают перезапуск. Незатронутое поле продолжает получать автоматическое значение. Входящий результат, ошибка или ответ уже выполняющегося запроса не отменяют ручные значения. Само редактирование не отправляет запросов backend и не запускает AI. Каталоги прежних версий без ручных значений продолжают открываться.

## Повтор и замена фото

В неуспешной карточке можно явно повторить обработку. Для фото на человеке или нескольких вещей предлагается заменить снимок. В готовой карточке действие «Проблема с вырезкой» открывает повтор и замену; обязательного подтверждения результата нет. Ожидающее фото также можно заменить.

Повтор создаёт новую операцию с тем же снимком, замена — новую операцию и снимок, но идентичность вещи и ручные тип/цвета сохраняются. Новая попытка записывается локально до сети; несколько офлайн-замен доставляют последнюю версию. До готовности новой вырезки показана прежняя с явной подписью. Её режим demo/live сохраняется отдельно от режима новой обработки. Старые ответы и скачивания проверяются по операции и не могут перезаписать новую попытку.

Клиент и backend обновляются вместе: новые URL результата привязаны к операции, а старый клиент их не понимает. Новый клиент читает прежний каталог и `result.png`; откат на старый клиент после замены фото небезопасен — он не знает новых имён файлов и номеров версий.

Файлы снимков и результатов имеют отдельные имена по версии/операции; каталог переключается на результат только после записи PNG. Старые версии сохраняются вместе с вещью и очищаются при её удалении. Редактирование полей не запускает новую обработку; явный повтор или замена могут вызвать провайдеров согласно настроенному режиму backend.

## Удаление

«Удалить вещь» доступно у ожидающей, готовой и ошибочной карточки, включая работу без сети. Карточка исчезает после надёжной локальной записи, а команда серверу переживает перезапуск и автоматически отправляется при восстановлении связи в открытом приложении. Удалённое до загрузки фото не отправляется. Поздние ответы не возвращают карточку.

Удаляется вся локальная папка вещи со всеми версиями фото и вырезок. Если очистка не завершилась, её намерение сохраняется и повторяется после перезапуска. Ошибка сохранения самого каталога оставляет карточку на месте и показывает сообщение. Серверная команда идемпотентна: потерянный ответ можно безопасно получить повторным запросом. Прежний каталог-массив читается; новое сохранение использует объект с вещами и очередью удаления, поэтому откат на прежний клиент после сохранения небезопасен.

## Подтверждение доставки и срок хранения

После записи вырезки готовая карточка и команда подтверждения сохраняются одним обновлением каталога. Только после этого клиент отправляет подтверждение конкретной операции. Очередь переживает перезапуск и потерю ответа, продолжает работу в открытом приложении и не меняет уже сохранённую карточку. На backend фото и результат очищаются после подтверждения; локальный исходник, вырезка и поля остаются доступны без сети. Старое подтверждение не затрагивает новую попытку обработки той же вещи.

Незабранные серверные данные истекают через 7 дней с загрузки. Клиент показывает причину и предлагает явно повторить обработку из сохранённого исходника; автоматического нового AI-вызова нет. Истечение во время скачивания обрабатывается так же. Прежняя хорошая вырезка и ручные поля сохраняются при повторе.

Каталоги прежних версий продолжают открываться. Для прежней готовой карточки подтверждение добавляется только при наличии читаемой локальной вырезки и после сохранения очереди. При обновлении backend старые серверные записи без известного срока считаются просроченными: готовые локальные карточки от этого не теряются, незавершённые можно повторить. Для остановленного dev-стенда с публичными фото очистка может ждать запуска; это исключение не задаёт срок хранения личных фото или удаления у внешних провайдеров.

## Simulator UI E2E

На Mac из корня репозитория запустите управляемые внешние HTTP-ответы, затем настоящий backend с отдельным тестовым каталогом, затем прокси. Это тестовые ключи; реальные API не вызываются.

```bash
NODE_ENV=test node backend/test/providers/ui-server.mjs
```

Создайте файл управляемого времени для тестов. Один и тот же абсолютный путь нужно передать backend и прокси; обычный запуск приложения его не использует:

```bash
printf '{"offsetMs":0}\n' > /tmp/saint-look-ui-clock.json
```

В другом терминале:

```bash
NODE_ENV=test SAINT_LOOK_TEST_CLOCK_FILE=/tmp/saint-look-ui-clock.json SAINT_LOOK_PROVIDER=live \
SAINT_LOOK_TEST_PROVIDER_ORIGIN=http://127.0.0.1:8789 \
TYPESAFE_API_KEY=fixture-typesafe-key PHOTOROOM_API_KEY=fixture-photoroom-key \
SAINT_LOOK_PROVIDER_PREFLIGHT_CONFIRMED=true SAINT_LOOK_STAGE_DELAY_MS=100 \
SAINT_LOOK_OWNER_TOKEN=saint-look-ui-tests-owner-token-00000001 \
SAINT_LOOK_DATA_DIR="$(mktemp -d)" node backend/src/server.mjs
```

В третьем терминале запустите прокси, в четвёртом — тесты:

```bash
NODE_ENV=test SAINT_LOOK_TEST_CLOCK_FILE=/tmp/saint-look-ui-clock.json node client-ios/scripts/ui-test-proxy.mjs
```

```bash
./client-ios/scripts/test-simulator.sh
```

Для отдельного сценария можно ограничить запуск; без переменной выполняются все UI-тесты:

```bash
SAINT_LOOK_UI_TEST_ONLY=SaintLookUITests/WardrobeFlowTests/testDeletingTwoOfflineThingsSurvivesRelaunchAndNeverUploadsTheirPhotos \
./client-ios/scripts/test-simulator.sh
```

Тестовый провайдер слушает только loopback `8789`. UI-тесты сбрасывают его счётчики и задают одноразовые внешние отказы через `/__control`, защищённый тестовым токеном. Адрес и токен задаются `SAINT_LOOK_UI_PROVIDER_CONTROL_URL` / `SAINT_LOOK_UI_PROVIDER_CONTROL_TOKEN`; по умолчанию `http://127.0.0.1:8789/__control` и `saint-look-ui-provider-control-token-00000001`. Несмотря на протокол live-провайдеров, backend явно возвращает `mode: demo` при тестовом HTTP-origin.

Прокси слушает только `127.0.0.1:8788` и принимает только loopback upstream с режимом demo. Тесты управляют разрывами соединения через защищённый тестовым токеном `/__control`; рабочий backend таких маршрутов не имеет. Фото и токены в диагностический вывод не пишутся. Для проверки срока тестовый контроль меняет только смещение часов в общем файле `SAINT_LOOK_TEST_CLOCK_FILE`; данные гардероба напрямую не изменяются. Смещение ограничено 0–365 днями, сброс сценария возвращает его к нулю. Backend разрешает этот режим только при `NODE_ENV=test` с управляемыми loopback-провайдерами. Прокси умеет отключить передачу до приёма, оборвать ответ уже после приёма загрузки, удаления или подтверждения настоящим backend и удержать один ответ с изображением результата до команды теста (не более 12 секунд). Удержание снимается также при разрыве соединения, сбросе режима или остановке прокси.

Скрипт выбирает доступный iPhone Simulator или использует `SAINT_LOOK_SIMULATOR_UDID`, отключает параллельные клоны и сохраняет `.xcresult` в `client-ios/build/`. Приложение теста подключается к прокси `http://127.0.0.1:8788`; альтернативные адрес/токен задаются `SAINT_LOOK_UI_TEST_URL` / `SAINT_LOOK_UI_TEST_TOKEN`. Управление использует `SAINT_LOOK_UI_TEST_CONTROL_URL` (по умолчанию `http://127.0.0.1:8788/__control`) и `SAINT_LOOK_UI_TEST_CONTROL_TOKEN` (по умолчанию `saint-look-ui-control-test-token-00000001`). Переменные должны быть доступны test runner. Для другого порта backend задайте прокси `SAINT_LOOK_UI_PROXY_UPSTREAM`, для порта прокси — `SAINT_LOOK_UI_PROXY_PORT`. Обычные настройки приложения эти переменные не читают.

Тесты через UI добавляют фото, наблюдают pending → ready, проверяют тип/цвет и сохранение результата после перезапуска с недоступным backend. Остальные сценарии проверяют сохранение фото при ошибке сети, несколько офлайн-добавлений с перезапуском и автоматическим продолжением без ручного действия, а также потерю ответа уже принятой загрузки без второй вещи. Дополнительные сценарии проверяют локальные правки до автоматического результата, во время доставки вырезки и после готовности, сохранение после перезапуска и отсутствие новых загрузок при редактировании. Сценарии #6 проверяют ошибку квоты и явный повтор, замену неподходящего снимка, прежнюю вырезку и ручные правки при нескольких офлайн-заменах и после перезапуска. Снимок элемента UI сравнивается до и после замены: новый красный исходник не подменяет прежнюю синюю вырезку, пока не готов новый результат. Сценарии #7 удаляют две ещё не отправленные вещи без сети, готовую вещь с потерей ответа удаления и ошибочную карточку; проверяют перезапуск, автоматическую доставку и отсутствие лишних загрузок. Сценарии #8 проверяют сохранность готовой карточки после очистки серверной копии, устойчивое подтверждение после перезапуска и потери ответа, а также истечение семи дней и явный повтор из локального фото. Скрипт сначала выполняет `build-for-testing`, затем добавляет HTTP-исключения только для loopback в plist сгенерированного UI test host и запускает `test-without-building`: настройки ATS приложения не распространяются на отдельный test host. Внешний AI не вызывается. Детерминированная кнопка обходит только системный выбор фото; сам PhotosPicker этими тестами не проверяется.

В CI прогон UI-тестов записывается в MP4. Запись доступна в артефакте `simulator-ui-video` соответствующего GitHub Actions run и хранится 7 дней. Для локальной записи запустите скрипт с `SAINT_LOOK_RECORD_VIDEO=1`. Видео показывает автоматические сценарии Simulator; ручную проверку PhotosPicker оно не заменяет.

В среде реализации Linux нет Xcode; результат hosted Simulator-прогона фиксируется в PR. Отложенная ручная проверка системного PhotosPicker отслеживается отдельно в [#13](https://github.com/tbb/saint-look/issues/13).

## Проверка Fly.io dev-стенда

Отдельный `RemoteDeploymentTests` по умолчанию пропускается; прежние 14 локальных сценариев продолжают работать. Manual deploy workflow запускает только этот класс после проверки точного SHA и уникального маркера выкладки через публичный API. Simulator напрямую подключается к HTTPS, добавляет синтетическое фото, получает готовую demo-карточку и проверяет её после офлайн-перезапуска. Прокси и локальные control endpoints этому сценарию не нужны. Видео хранится 7 дней в артефакте `remote-simulator-ui-video`; токен в интерфейсе не показывается.

Для ручного запуска на Mac нужны `SAINT_LOOK_REMOTE_URL`, `SAINT_LOOK_REMOTE_REVISION` (40 символов), `SAINT_LOOK_REMOTE_DEPLOYMENT_ID` и секрет `SAINT_LOOK_REMOTE_TOKEN` в окружении. Введите токен без вывода и записи в историю:

```bash
read -rs SAINT_LOOK_REMOTE_TOKEN
export SAINT_LOOK_REMOTE_TOKEN
SAINT_LOOK_REMOTE_SMOKE=1 \
SAINT_LOOK_UI_TEST_ONLY=SaintLookUITests/RemoteDeploymentTests \
SAINT_LOOK_RECORD_VIDEO=1 bash client-ios/scripts/test-simulator.sh
unset SAINT_LOOK_REMOTE_TOKEN
```

В конце сценарий удаляет карточку через UI и даёт очереди удаления время на отправку. Это не отдельное доказательство серверной очистки: её проверяет API smoke. При прерывании UI-прогона на стенде может остаться синтетическая запись; серверные изображения очищаются подтверждением или сроком хранения. Проверка сохранности volume при redeploy/rollback описана в [runbook](../docs/deployment.md). Успешный локальный CI с пропущенным remote-классом не доказывает работу Fly.io: до настройки аккаунта нужен отдельный реальный прогон.
